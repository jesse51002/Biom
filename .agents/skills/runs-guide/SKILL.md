# Automations and runs

**An automation is a folder under a page. A run is a process the server starts from it, in a directory of its own, with a row and a log that outlive it.** The framework holds the mechanism — start, track, end, show — and nothing about what a run means. That is the page's, and it is the whole of the design: the workspace runs no inference and owns no agent loop, it presses the button on a command the person already has and watches. The workspace's Architecture page `Automations` is what this build defers to; `vault/docs/automations.md` is the same story for the person whose folder it is. This file is for whoever changes the code.

## 1. What the framework reads, and what it refuses to know

**The manifest, and nothing else in the folder.** `automation.yaml` is narrowed by `manifestOf` in `server/domain/runs.ts` into `AutomationManifest`: a name, a description, an `agent` label, `env` as a list of names, `command` as a list of arguments, `inputs` as declared fields. Every other key is dropped; a key that is the wrong shape is refused with one sentence, and a folder whose manifest will not read is LISTED with that sentence rather than hidden — a folder somebody wrote is a thing to repair. A folder is an automation when it holds the manifest; `kickoff.md`, `INSTRUCTIONS.md`, `skills/` and `code/` are read only to be copied or linked.

**No agent by name.** `agent` is a word for people. There are no adapters, no vendor's event stream is parsed, no session is captured and nothing resumes anything. Every harness the workspace uses is a command on the server's `PATH` with a flag that grants it the vault, and the harness table in §7 is the whole of what the framework knows about any of them — which is to say, nothing at runtime.

**`command` is a list and never a shell string**, so an input cannot become a second command. `substitute` fills `{name}` for each input and `{vault}`, `{run}`, `{kickoff}` for the four things the framework knows, in every argument and in the kickoff; a `{word}` that names none of those is left as it was, because a prompt that says `{like this}` in prose is not a template error.

**`env` is names.** `start` checks every name present in the environment the server was started with and refuses by name before anything is written; the values go into the process's environment and nowhere else — never a file, never a row, never the wire. `env.names` on the outer ring answers the names the server holds and nothing about them, for the manifest form's picker.

## 2. Three INSTRUCTIONS.md, one AGENTS.md per run

`INSTRUCTIONS.md` is the person's, at three levels — the workspace's at the vault root beside the seeded `AGENTS.md`, the page's beside `content.yaml`, the automation's beside its manifest — and each outranks the one above it. `AGENTS.md` is the framework's at every level: the vault's is seeded, the run's is generated by `runAgentsMd` and written into the run directory as the same text every run. It is what a harness that walks parents finds first, because it is in the working directory, and it says where the vault is, which three files to read in what order, that rows go through the API at `$BIOM_API`, and which inputs this run has. **Nothing is prepended to the prompt**: the kickoff is the author's file, substituted and nothing more. `CLAUDE.md` in the run directory is a link to that `AGENTS.md`, for the one harness that reads only its own name.

## 3. The run directory

`start` assembles `<vault>/.biom/runs/<id>/` before it spawns, through `RunFs` in `server/platform/rundir.ts` — the platform half `Files` deliberately cannot be, because a run directory holds links and byte-addressed logs. The rule for each entry:

| Entry | How | Why |
|---|---|---|
| `automation.yaml`, `INSTRUCTIONS.md` | copied | the record of what ran |
| `kickoff.md` | copied, inputs written in | the record of what was asked, whole |
| `skills/`, `code/` | linked to the automation's | an environment built for them later is the automation's, and the vault's commit already records their version |
| `page/INSTRUCTIONS.md` | linked to the page's | two levels arrive as two files; nothing is merged |
| `vault/` | linked to the vault root | ONE link, never one per page — per-page links go stale the moment a run makes a page |
| `AGENTS.md`, `CLAUDE.md → AGENTS.md` | written | §2 |
| `.agents/skills/`, `.claude/skills/` | linked to `../skills` | where each harness looks, both pointing at the one folder |
| `.claude/settings.json`, `.codex/config.toml`, `opencode.json`, `.gemini/settings.json`, `.cursor/cli.json` | written by `harnessFiles` | each grants the vault's REAL path; §7 |
| `stdout.log`, `stderr.log` | the process's | opened here, handed to the kernel as the child's two outputs |

`content.yaml` stays behind: it is the page, not the automation. **The assembly is one guarded step**: a copy, a link or a harness file that fails takes the half-made directory with it and refuses as `bad_request` naming what failed, so nothing is spawned into a directory missing its kickoff and no `.biom/runs/<id>/` is left behind with no row. Scratch written into the run directory stays there; only what goes through `vault/` or the API is real. **The directory is already the shape of a container** — the working directory is the run's, the vault link is a bind mount, the environment is the environment, the logs are the two streams — so a runner that takes it into an image changes nothing above `start`.

## 4. The environment, and the line that carries the deferral

The process gets `ENV_FLOOR` — `PATH`, `HOME`, `USER`, `SHELL`, `LANG`, `TMPDIR` and their kin — `BIOM_VAULT`, `BIOM_RUN`, `BIOM_API` (the address the server answers this vault at, with the launch's token where there is one), every name the manifest asked for with its value, and nothing else of the server's. **The floor is the one deliberate exception** to *nothing else*: a harness finds its login and its settings under the person's home, and without `HOME` a run cannot authenticate as the person, which is the premise. `BIOM_SHELL` is never in it.

**The line that inherits `PATH` carries the comment**, and the comment is the design: dependencies are deferred by decision rather than oversight. What ships later, designed so nothing built today has to change — `runtime:` in the manifest naming a language and version, a lockfile beside `code/` (`pyproject.toml` + `uv.lock`, or `package.json` + `bun.lock`), one environment per lockfile hash built under `.biom/envs/<hash>/` and put FIRST on this `PATH`, and an ignore file for it. No `install:` step and no Dockerfile, then or now. Until then every command runs on the machine it is on with the server's own `PATH`, and a built application launched from a desktop carries a different `PATH` from a terminal — the trap this closes for `code/` and leaves open for the harness CLI itself.

## 5. The process, the group, the kill, the reconcile

`server/platform/process.ts` is layer 1 and knows no vault: `start` spawns with `detached: true` so the child leads a session and a process group of its own, stdin `ignore` so a harness that finds a terminal on stdin gets end of file instead, and the two outputs as file descriptors the kernel writes — nothing here buffers, and a server that restarts leaves the log exactly as far as the child got. `end(pgid, grace)` is `kill(-pgid, TERM)`, a poll until the leader is gone or the grace is spent, then `kill(-pgid, KILL)`; the group is the whole point, because `make` starting `python` starting a harness starting a shell is four processes, and a signal to the pid alone orphans three. Windows has no groups: there the pid is the group and the tree ends with `taskkill /T`, the one platform branch in the file. A command that does not exist settles `done` with `exit: null` and the error's code as the `signal` word rather than never.

`KILL_GRACE` is 5 seconds, a number the build picked as the spec left it. `kill(id, by)` records who — `page` off the wire, `screen` from the overview, `shutdown` from the exit path — and a kill on a row this server never held a process for (one reconciled after a restart) finishes the row itself, because nothing else will.

`reconcile()` runs on every mount before anything reads the table: every row still `running` whose process is not alive is marked `lost`, never restarted. **Alive is the pid AND its birth**: `start` records `born` — the process's start time, field 22 of `/proc/<pid>/stat` on Linux and `ps -o lstart=` elsewhere — and `alive(pid, born)` answers no for a pid wearing a different birth, which is what a pid reused after a reboot is. Without it a row from before the reboot was counted live, held the window's close, and was sent a KILL meant for a process that had been somebody else's for a day. `kill`, `reconcile`, `endAll` and `killAll` all pass the row's `born`; a row with none — written before the column existed — is judged by the pid alone. **Two endings, and every route passes through the second.** `endAll("shutdown")` is the graceful one — TERM, the grace, KILL, each row marked — and `Host.endRuns` calls it for every mounted vault on `SIGINT` and `SIGTERM` (`endRunsOn`) and when the shell's stdin pipe closes (`exitWhenTheParentGoes`). `killAll("shutdown")` is SYNCHRONOUS — KILL every live group now and mark every row — and `Host.killRuns` calls it from the process's own `exit` handler, beside the terminals' `killAll` and for the same reason: no timer runs after `exit` and nothing can be awaited there, and a signal handler that exits before an async ending finishes (the shell's kill is one) would otherwise leave the group alive. A run is its own group, so a Ctrl-C at the terminal does not reach it and the registry has to. `SIGHUP` is left alone on the terminals' argument: `make up` starts the server under `nohup`.

## 6. The registry, the kinds, the identity, the stream

**`.biom/runs.db` is the second database under a vault**, opened by `server/main.ts` through `makeDb` and handed to `makeRuns` exactly as `workspace.db` is handed to `makeTables`; `runs.ts` is the third file allowed to hold SQL, and `db.ts`'s header says so. `.biom/.gitignore` is written once, saying `*`, so nothing under it is ever in git; the watcher excludes `.biom` by name so a log growing never redraws a page. One table, `runs`, a row written on start and rewritten on end: `id`, `page` (the page that HOLDS the automation), `uid` (that page's identity), `automation`, `started_by` (provenance — the `uid` of the page whose box pressed the button, null for the workspace's own screen), `command` as it was started, `inputs`, `pid`, `pgid`, `started`, `ended`, `status`, `exit`, `signal`, `ended_by`.

**The six host kinds** — `automation.list`, `run.start`, `run.list`, `run.get`, `run.read`, `run.kill` — were the eighth contracts edit, taken at its own barrier on 2026-09-17. A page may see every automation, start any, read any run and end any: the ring is not the wall. What will narrow a list, a row and a log is the asker's VIEW permission on the row's `page`, from the sync engine's model, and this build carries no filter and no seam for one — `routes.ts` answers in full, and the filter is written there when the model lands. **The stamp is the bridge's**: `run.start` in `client/bridge/bridge.js` writes the mounted page's `uid` into `by` over whatever the box sent, so *started by* is a fact the browser enforces. `run.kill` carries `by` too — `"screen"` from the workspace's own screens, which the store sends, and `"page"` for a box, which the bridge forwards WITHOUT the field so a page cannot claim the screen — and `ended_by` records which. The outer ring carries `run.live` (alive across every mounted folder, answered on the UNPREFIXED route beside the vault kinds because the shell asking it has no folder in mind), `page.files` / `page.readFile`, `automation.get` / `automation.set` (the manifest as a structure; the server writes the yaml, so a hand-edited file and a form-edited one are the same file — and `setManifest` refuses what is not a map or will not read back before a byte lands, so the form cannot write a manifest the next `start` would choke on), `automation.templates` / `automation.create`, `env.names`, and `vault.files` / `vault.readFile` / `vault.writeFile` (the vault's `INSTRUCTIONS.md` and `.agents/skills/` and nowhere else, a seeded skill marked so the screens leave it out).

**`run.read` is bytes from an offset**, `RunRead`: text, the next offset, and whether the run has ended. `completeUtf8` holds back a character cut by `max` so the next read starts on it, except at the end of a finished file. A page follows a live log by reading again and stops when `ended` is true and the offset has caught up; the overview and the Runs screen do it once a second while something is alive and stop when nothing is — through `followLog` in `client/widgets/runsui.js`, which reads up to `READS_PER_DRAW` chunks per draw until a read comes back empty, so a run that ended between two draws is read to its end rather than one chunk behind, and keeps the last `TAIL_KEEP` characters. Both views hold it as a `const` above their `return`: the screens are hoisted functions that run after the factory has returned, and a `const` under that return is one they can name and never reach.

**`uid` is the page's identity**, minted by `pages.ts` on `create`, written into every page that has none by `identify()` on mount under one commit, carried on `PageRef` and `Page`, kept through a move, and refused by the codec when it is not one (`UID` in `contracts/types.ts` is the grammar). A run names it, so a page moved under another parent still owns the runs it started: **the registry's rows are re-pointed, never re-resolved on read.** `page.move` and `page.rename` in `routes.ts` call `runs.relocate(from, to)` beside `restack`, which rewrites `page` on every row under the old id and its descendants; `runs.relocateAll(refs)` does the same by identity — every row whose `uid` names a page now at another id — on mount after `reconcile()` and again in `settle` whenever a burst was structural, which is how a page moved outside the app catches up. So `run.list` is ONE query by `page` and `automation`, `run.get` no lookup at all, and the once-a-second polls walk no page list. A run whose page is gone keeps its old id, which the screens say. **A page carrying `uid:` refuses on a server older than this one**, because the page's top level is closed by name; there is no format bump, and the workspace is pinned to a tag.

**A run starting or ending is one payload-free event on the vault's stream**, said by `announce` in `main.ts` to the same subscribers a changed file reaches. Nothing on disk moved that the watcher would report, so the registry says it itself; the screens reread `run.list` on it.

## 7. Pointing each harness at the vault

The run directory is inside the vault, and a sandbox does not follow that on its own: Claude Code checks both ends of a symlink, Codex's Linux sandbox refuses a write that crosses one, and both ignore a project config file on a folder that has not been trusted — which a run directory never has been. So the grant travels on the command line in the template's command, and `harnessFiles` writes the config file anyway, for the harnesses that honour it and as the written intent for the ones that do not. Checked on 2026-09-17; this table is kept current here and nowhere else.

| Harness | Grant the vault | Carried in the run dir | Instructions it reads |
|---|---|---|---|
| Claude Code | `--add-dir {vault}`; `--permission-mode acceptEdits` auto-accepts edits there | `.claude/settings.json` `permissions.additionalDirectories` — ignored on an untrusted folder in `-p` | `CLAUDE.md` in cwd and parents, never `AGENTS.md`; the run's `CLAUDE.md` links to its `AGENTS.md` |
| Codex | `--add-dir {vault}` or `-c sandbox_workspace_write.writable_roots=["{vault}"]` | `.codex/config.toml` — loaded only for trusted projects | `AGENTS.md` in cwd and parents |
| OpenCode | `permission.external_directory: allow` in `opencode.json` | honoured as written | `AGENTS.md` |
| Gemini CLI | `--include-directories {vault}` | `.gemini/settings.json` `context.includeDirectories`, `context.fileName` naming `AGENTS.md` | `GEMINI.md`, or whatever `fileName` names |
| Cursor CLI | `Read(...)`/`Write(...)` globs naming the vault | `.cursor/cli.json` — permissions are the one key allowed at project level | `AGENTS.md`, `CLAUDE.md` |
| OpenClaw | `--cwd {vault}`, or `tools.fs.workspaceOnly: false` | the gateway's, not a file here | `AGENTS.md` from its workspace, not cwd |
| Hermes | no sandbox on the local backend; `--in {run}` | `~/.hermes/config.yaml`, not per run | `AGENTS.md` from cwd |
| Aider | no sandbox; start it in the vault with `--file`/`--read` | `.aider.conf.yml` from cwd | `CONVENTIONS.md` via `read:` |

**Two things every row shares.** The grant names the vault's real path, never the `vault` link, because two of the sandboxes resolve it and one refuses it. And what every harness reads on its own is the run's `AGENTS.md`, which names the three `INSTRUCTIONS.md` in reading order.

**The templates** New copies are `server/runs/templates/<harness>/` — the framework's, beside its code, never in the vault; `tools/app.ts` carries them into the binary. `automation.create` copies one under the page and rewrites the manifest's `name` to what the person called it; the copy is the workspace's from that moment, and nothing is seeded or updated. A template that will not read is left out of the list rather than offered.

## 8. The screens, and the close

Three views, one widget file. `client/views/runs.js` is the rail's overview: Running now, Finished, Start's three steps in place (pick from every page that holds one, set the inputs with the already-running warning, Start), Kill, the last line of stdout raw and the whole log on a click, every page named a link to the page. `client/views/instructions.js` is the rail's Instructions — the vault's `INSTRUCTIONS.md` and its own skills in one tree with ＋ on the folder, never the seeded set — and a page's Instructions, one editor over its `INSTRUCTIONS.md` under one line to hand your agent. `client/views/automation.js` is a page's Automations: the strip and New, templates as tiles, and per automation Manifest (a form; `automation.set` writes the yaml), Files (the tree — the kickoff, the instructions, `skills/` and `code/`, never the manifest, which is the Manifest screen — with the workspace's skills greyed as a second root, ＋ on `skills/` and `code/`, the editor beside it) and Runs. `client/widgets/runsui.js` is the line to hand your agent, the autosaving editor (`SAVE_AFTER`, the word that says `saving…` and `saved`), the file tree, `nameField` and `followLog`, drawn once for all three — the views are siblings and cannot share a line otherwise. **A name is asked in place, never by `window.prompt`**: Electron's renderer throws on `prompt()`, so New's template tile, ＋ on a folder and ＋ on the skills folder each draw `nameField` where the editor was — Enter takes it, Escape cancels, a refusal lands beside the field. **Every autosave is a QUIET write and the file's opening is the one commit**: `page.writeFile`, `automation.set` and `vault.writeFile` take `quiet`, the store skips its re-read and emit for one, and each editor says `vault.commit` (`commitVault`, *Before … was edited*) as it opens — so what the vault held before this sitting is one revert away and the pauses in typing are not each a version, where every 700 ms save was a commit and a redraw of the canvas before. The store methods are never cached and never emit: a run's row moves on its own clock and the stream says when.

**The bar's two controls** stand where the three dots were: `pageView` is `page`, `instructions` or `automation` — put back on `UiState` by this edit after the fifth took it out with the Config screen, and three members wide, every one in every build, so there is no door to guard and no hide set. They go before the terminal's toggle, which stays the rightmost action. `runs` and `instructions` joined `ViewName` and `VIEWS` and are in every build. Every one of the three screens fills the canvas: `.plate[data-face=…]` in `client/css/runs.css`.

**Closing over a live run asks.** `holdTheClose` in `app/main.js` holds the window's own `close` event — so the bar's button, Alt+F4 and a window manager's close all run through it — asks the server `run.live` on the unprefixed route with the launch's token, and where anything is alive pushes the count on `biom:window-closing`; the shell draws the question in the bar (`CLOSE_WORDS`), yes is `windowControls.close(true)`, the one way past the hold, after which the server ends every run on its way out through the stdin pipe. A server that does not answer has nothing to keep running and the window closes at once — the ask carries `AbortSignal.timeout(2000)`, so a server that is up and not answering cannot hold the window open for its socket's whole patience.

## 9. Deliberately not here

Access (§6 — the view permission on the row's `page`, when the sync engine has a model; a run whose page is gone is everyone's to see and end). Dependencies, runtimes, lockfiles, containers (§4). A scheduler, a queue, a retry: a run is a button pressed by a person or by a page. A secret in a form: `env` names are checked present and never read or drawn. Any parsing of a log.
