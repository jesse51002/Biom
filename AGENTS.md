Conventions for the framework in this directory.

# What this is

This is the framework — the development framework whose developers are agents.

**Its public surface is the part expected to outlive any given implementation; the rest is still expected to change freely, and that stays true.** The host-to-guest contract — `client/frame/frame.js`, `client/bridge/bridge.js` and `guest/biom.js` — and the vault format are that surface, because a contract is expensive to change once artifacts exist in the wild. Everything else here is written to be replaced.

**The mechanics live in guides now, not in this file.** `.agents/skills/*-guide/` holds one guide per subsystem — the boundary, the section runtime, the page format, plugins, the terminal — each the single source of truth for its own, each ending in a Key files map, and each updated in the same change as the code it describes. This file keeps the CONVENTIONS: how to work here, what the gates are, and the rules that bind every subsystem at once. When you need to know how something works rather than how to work on it, the guide is the answer and this file is not.

```
make dev      # http://localhost:4400
make app      # build the application and install it where this desktop finds it
make check    # layering, then types, then every client module parses
make graph    # the dependency diagram, derived from the real imports
make fresh    # drop the per-user default vault; the next dev run reseeds
make browser  # the Chromium the browser tools drive; once per machine
make help     # the rest
```

# The layering rule

**A module may import only from a strictly lower layer, plus layer 0. No sibling imports, ever.**

The layer of a module **is** the directory it sits in. There is no per-file judgement, no exceptions list, and no argument about whether something counts as a util. `layers.json` is the whole map, and `tools/layers.mjs` fails the build on any upward, sibling or cross-tier edge.

**When two modules in a layer need each other, the shared thing moves down a layer.** That is the entire conflict-resolution procedure. Reaching sideways is the moment the rule exists to stop.

**The composition roots are at the top.** `server/main.ts` and `client/boot.js` are the only modules that construct anything; everything below receives its dependencies as arguments. That is what makes *replace a module without touching others* literally true — a swap is one changed line in a root.

**The only upward mechanism is a callback.** Views subscribe to the store through `contracts/emitter.js`; the store never imports a view. Calls descend through imports, data ascends through subscriptions a higher layer registered. Nothing anywhere holds a reference to a module above it.

**Static imports only, one per line, at the top of the file.** This is not taste — it is what makes the gate a regex instead of a parser. A dynamic `import()` is reported rather than failed, for the one legitimate case: an optional bundle loaded on demand. **There is exactly one, and it is named in `tools/layers.mjs`** — the composition root reaching `dist/embedded.ts`, the generated manifest of everything a compiled binary carries, which a clone that has never run `make app` does not have and must still start without. `make types` generates one first through the `manifest-stub` target, because `tsc` follows the import even though the runtime does not — an EMPTY module, which is all a file opening with `@ts-nocheck` can be checked for, and which copies none of the repository into `dist/files/` on every `make check`. Only `make app` writes the real one.

**`contracts/` is frozen.** Changing it is the one edit that touches every module, so it happens at a barrier and never while parallel work is in flight. If a type is wrong, stop and say so rather than widening it locally.

# Rules

**No build step on the client, ever.** `client/` is plain JavaScript a browser loads directly, typed through JSDoc and checked by `tsc --noEmit --checkJs`. A transpile step between *Claude Code writes the file* and *you press reload* breaks the exact loop this instrument exists to demonstrate. `server/` and `tools/` are real TypeScript because bun runs it natively at no cost, and that is the half with invariants worth checking mechanically.

**The artifact frame is `sandbox="allow-scripts"` with no `allow-same-origin`.** It has an opaque origin, so it cannot reach the server directly even though the server is right there, and every path to workspace data is forced through the port. The browser enforces the chokepoint for free.

**ONE PERMISSION IS DELEGATED BACK OVER THAT WALL AND IT IS THE CLIPBOARD'S WRITING HALF.** `allow="clipboard-write"` on the frame, with the argument beside the attribute in `client/frame/frame.js`. Permissions policy reads an opaque origin as a cross-origin child, so its allowlist is empty unless the container says otherwise — measured: `navigator.clipboard.writeText` in the box fails as *blocked because of a permissions policy applied to the current document*, and the refusal lands in a console nobody reads, which is why a page carrying a path or a prompt could only offer a Copy control that selected the text and hoped. **`clipboard-read` is deliberately absent**: reading the clipboard is taking something nobody offered. The browser still wants a real gesture and a focused document before a write, so what is delegated is an act a person has to make — and a page whose control refused focus on `mousedown` has to take it back in the click, which the root page does. **It is not a `contracts/` edit and must not become one**: a `clipboard.write` kind was the alternative and an iframe attribute is smaller than a wire kind.

**Its consequence is load-bearing: the host can never read what is inside the box.** The section count, and anything else the host wants to know about a page, is **self-reported**, not scraped. When you need a new fact about a page, add a `GuestNotice` — do not reach into the frame, because you cannot.

**A tool outside the browser can see it, and that is how a page is checked without a person at the screen.** A Playwright MCP driving the Chromium that `make browser` fetches is what gives a session its `browser_*` tools; registering it is the agent harness's own configuration and is not a file this repository ships. Open `http://localhost:4400/?vault=<absolute vault path>#/page/<id>`, wait until the status strip reads `Drawn` followed by a number (`browser_wait_for` on that text — it is the `ready` notice, and nothing before it is the page), then snapshot or screenshot. The snapshot reaches inside the box and its refs can be clicked and hovered; a `[artifact]` warning in the console is the box reporting an error. Two routes were measured to fail, so nobody rediscovers them: a raw `chrome --headless --screenshot` fires before the handshake and shows an empty box, and **the Claude Code in-app Browser pane refuses every request an opaque-origin frame makes** — the runtime never loads there, `Drawn not reported` is all it will ever say, and it must not be used to check a page.

**The handshake is in two halves, and the split is not cosmetic.** `hello` goes over `window.postMessage` the instant the shim runs, before any other script in the box, and buys the ports. `ready` follows over the privileged one once the runtime has drawn, carrying the SECTION count. It must stay this way: a `<script type="module">` is deferred and `DOMContentLoaded` fires only after deferred scripts finish, so a handshake that waited for that event would be waiting on the very script that is waiting on the handshake — a page with a top-level `await biom.data()` would stall until the call timeout and then render nothing. Writing a module script with a top-level await is an entirely ordinary thing to do, so the contract accommodates it rather than forbidding it.

**TWO ports are granted, and which one a message arrived on is the whole of the authorisation.** The runtime reads the page and writes its shape back; a section must never be able to. So `hello` is answered with `{ kind: "ports", g, page }` and a transfer list — **privileged first, ordinary second** — and the bootstrap publishes them as `window.__g = { runtime, guest, page }`, which the runtime reads once and deletes. `bridge.resolve` answers the ordinary port and `bridge.runtime` the privileged one, each narrowing with its own guard. **Inside the box that split is a closure, not a browser guarantee** — section code shares a realm with the runtime. The browser-enforced wall is between the box and the app, and nothing here may describe the in-box split as a security boundary.

**One box per page, and it always fills.** There is no box per block and no self-sizing mode: one iframe takes the whole canvas, scrolls inside itself, and **never reports a height**. `FrameOpts` is gone and `GuestNotice` has no `size`.

That is a mechanism rather than a simplification. If the box sized itself to its content and the HOST page scrolled, the scroll container would be outside the box — `animation-timeline: scroll()` and `view()` would find no scroller, `position: sticky` would never stick, `100vh` would be meaningless and an `IntersectionObserver` would have no root. **Filling is what makes the box its own viewport**, and being its own viewport is the entire reason a section can drive a scroll effect. Do not put a height notice back.

**The chokepoint is a type, not a check, and there are three rings of it.** `HostRequest` ⊂ `RuntimeRequest` ⊂ `ApiRequest`: a section may say the first, the section runtime the second, the workspace UI the third. Each entry point narrows with a guard — `isHostRequest`, `isRuntimeRequest` — so there is no allow-list to keep in sync and no branch that can be got wrong. The framework grants unrestricted data access, so the inner ring is generous; it stays a separate type because narrowing it later must be one edit rather than a rewrite of every page.

**WHICH RING A KIND GOES IN IS DECIDED BY WHAT IT CAN REACH, NOT BY WHAT IT IS ABOUT, and `vault.info` is the case that says so.** *Which folder is this* used to be outer-ring with the other four `vault.*` kinds, on the rule that an artifact has no business knowing the workspace is a folder. It is inner-ring now, because **a person reading a page has to be able to point an agent at it** — everything here is edited by an agent opened in a directory, and a page that wanted to say where to start had to send the reader to a host screen or carry a path somebody typed into a variable, which is a fact that stops being true the day the folder moves. **What makes it safe is that it takes no argument**: the vault is an address rather than a message, so it asks about the folder the request was already addressed to and there is no field with which to name another. A page may know where it lives; it may not look around, and it may not move. `vault.browse`, `vault.open`, `vault.create` and `vault.recent` each NAME a folder that is not this one and stay where they are.

**The workspace UI is client zero of its own artifact contract.** The table grid issues the same `table.get` and `row.insert` an artifact does. A contract that cannot express what the grid needs cannot express what an artifact needs, and this is how that is discovered on day two.

**Ports are declared and never enforced.** `Port` and `Binding` ship; nothing is checked, and no screen shows them — the Config screen that was made for them went on 2026-09-17, because a screen for a thing the framework does not have was a screen saying so in one sentence. This is a decision, not an omission — see the decisions log in the build plan. Do not add enforcement without being asked, and do not delete the types to tidy up.

**The vault is a git repo, and that is an implementation detail.** The server commits before every agent write, so every version is kept and undo exists without an undo mechanism being built — which is also what makes the change somebody asked for a readable diff. But nobody using this touches the repo directly: reverting is a sentence you hand the agent, like everything else here. There was a History panel that said so over a prompt and *no version list yet*; the owner decided on 2026-09-17 that a placeholder for an undesigned screen goes rather than hides, and a version list, when one is built, is its own spec. Snapshot and rollback are out of scope by decision.

**ONE VALUE SAYS WHICH BUILD THIS IS, and it governs what is SHOWN and what is REFUSED — never how anything is loaded.** `BIOM_ENV` reads `development`, `test` or `production`; unset is development, and anything that is none of the three is read as production, because a typo in a build script must fail towards hiding. It is read in exactly two places: `server/main.ts` reads `process.env.BIOM_ENV` once — substituted at compile time by `--define` in a compiled build, the real process environment in a source run, one expression for both — and `client/boot.js` reads the meta tag in the document. **A SECOND VALUE TRAVELS THAT SAME CHANNEL AND NOTHING ELSE MAY JOIN THEM**: `biom-trouble`, why this launch has no workspace open, which cannot come down the wire because the client's one call before it has a folder is `vault.recent` and `VaultInfo` has no field for it — a `contracts/` edit, for a sentence. `withTrouble` in `server/main.ts` writes it and LEAVES THE TAG OFF when there is nothing to say, so a first launch's document is still byte-identical to the file; it stops being written the moment any folder opens, so it can never be a stale claim about a workspace somebody has since replaced. **The client has no build step, ever, so `/` is the ONE route the server composes** rather than serves flat: the same bytes with the value written into that tag, which in a development build is the value already there and therefore the file itself. Below those two lines the value is an ordinary dependency — a field on the API layer's `Deps`, one boolean into the shell and the views — and **no third module anywhere may ask an environment a question.** `development` and `test` show everything and refuse nothing.

**Nothing is deleted in production and nothing becomes a second code path.** Every module goes on being constructed and every view goes on existing; the value decides whether a row is put in the list a screen returns. A branch that removed a module in one build and not the other would be two applications sharing a name. **And the built application hides no screen.** The owner decided on 2026-09-17: the Map row is in every build and `#/map` opens it everywhere, and the two panels and the Config screen that were withheld are deleted from every build instead — History was a placeholder for a version list nobody has designed, Modify page gave directions to a terminal the dock now holds, Config was made for ports the framework does not have. With them went the sets that named what a build does not offer and the `offered` predicate that shut their second doors; a typed route reads the one `VIEWS`, and `parseHash` takes the hash and nothing else. **What production hides is a developer's diagnostics, and the rule is whether a person who never cloned this repository can act on it** — apply the rule rather than a list, because a list written here is a second one to keep. The sites are the `production` branches under `client/`, which `grep -rn production client/` finds — the status strip's counts and grant, the table's *Used by*, the `make dev` line on the failure screen — and every one of them is asserted BOTH WAYS in the suite: the rule the assertions are written under is the *EVERY ITEM ON THE PRODUCTION HIDE LIST* banner in `tests/shell.test.js`, and the tests themselves, wherever the view they cover is tested, are the only honest statement of what is on the list. **What it REFUSES is server-side, because a page can reach those without touching a control anybody could hide**: the `deps.production` arms in `server/api/routes.ts`, and nothing else anywhere. **That refusal is the one place production DOES less rather than shows less**, and it is the floor under a specified and unbuilt egress policy, rather than the design. `vault.browse` is one of those arms and it is LIVE: Browse was the only way to reach a workspace on disk and not in `Recent`, so it was held until the shell's folder dialog served Open as well as Create — it does, so `NATIVE_DIALOG` in `server/api/routes.ts` and its twin in `client/views/vault.js` are both true, and a test holds the two literals equal. **Which chooser the picker draws is not this value**: it is whether `window.biomShell.chooseFolder` is there, so the built application gets the dialog for Open and for Create's parent and draws no listing, and a browser gets the listing — which is why `make dev` is unchanged and why Create is on the production picker. **There are no per-feature switches, no settings screen behind any of it, and nothing here is configurable at runtime.**

**The refusal spends `unsupported`, which is its own word rather than the least wrong one.** It joined `HostErrorCode` at a barrier and means exactly *this build does not offer that* — the kind is known, the request was correct, and asking again will not help. It replaced `not_found`, which was what a closed enumeration with no right member left: `unknown_kind` was a lie, `bad_request` blamed a correct caller, and `limit` and `timeout` are retryable, so an artifact would have backed off and tried forever. The SENTENCE is still what a page author reads and it says the build refuses them. `refused()` in `server/api/routes.ts` is the one place it is spent.

**No SQL anywhere in the interface.** A table states where a column comes from as a relationship, never as a query. `biom.sql` exists on the wire for artifacts; nobody using this workspace should have to read a `SELECT` to understand their own data.

**Nothing sets a raw colour.** Every colour resolves to a token. **The chrome follows the vault**: the workspace UI takes the open folder's palette and its `furniture` face, so a folder that ships cream pages is a cream workspace to the edges of the window and one that ships a near-black biome is a near-black workspace. `client/theme/theme.js` writes them onto the root — `applyTheme`, called from `boot.js` on every store emit — and it writes two tokens beside them that no `theme.json` names: `--ui-face` from the furniture role, and `--shadow`, the palette's dark end, because depth mixed from near-white stock is a haze. It sets `color-scheme` too, so the chrome's own scrollbars stop being tinted dark under a light vault. What `client/css/tokens.css` declares is the FIRST FRAME and the fallback: `client/theme/palettes.js` is the one file allowed to name a colour, the test holds the two byte-equal, and the server fills any key a `theme.json` leaves out rather than letting the token go undefined. The box gets the same palette a different way — custom properties do not cross a document boundary, so it is handed the data over `theme.get` and re-declares it, and `var(--ink)` is not free in there. **AND DECLARING THE TOKENS IS NOT THE SAME AS WEARING THEM, which is the half that was missing.** The shim writes the palette onto `:root` and nothing else, so an element that names no colour inherits the browser's black — invisible while every palette was dark ink on light stock, and an unreadable page under the one this ships with. `guest/plugins/biom-doc/index.html` said otherwise for itself, so a `doc` page read correctly and nothing else in the same workspace did: the design doc, whose box is woven with NO document at all, drew its title and its whole shipped-default band in black on charcoal on a brand-new vault. The default ink is a fact about wearing the palette rather than about which plugin drew the page, so it is `INK` in `client/frame/frame.js` — woven into every box the host makes, ahead of the document's own head, in `@layer biom.ink`, which is what keeps it a default a section, a plugin document and a page somebody wrote all beat by existing. **One statement, and the doc plugin no longer holds a second.** **One value is the page's alone: `--paper`**, the palette's lightest stock, which `boot.js` sets so the sheet under the transparent box reads as a sheet laid on the workspace rather than as a hole in it. There is no Theme screen and there is not going to be one: a workspace is themed by the folder it opens.

**A page names the plugin that draws it, and a plugin is a page that reads a declared input.** `plugin: html` is the default and means the page's own `index.html`; `plugin: doc` is the section runtime; anything else is a document in the workspace's own `plugins/<id>/`. The host resolves the document server-side for the reason it resolves a section's markup: the box has an opaque origin and cannot fetch. A plugin's own configuration goes under `input:`, so the host's keys and the plugin's can never collide.

**A VAULT HOLDS ONLY THE PLUGINS IT WROTE OR OVERRODE, AND THE FRAMEWORK'S OWN ARE THE RUNG UNDERNEATH.** A page's document and a slot plugin are resolved nearest-first — the page's own `index.html`, then `<vault>/plugins/`, then `guest/plugins/` — and the framework's set is never the winner: a vault file at the same path replaces it by being there, and a vault with no such file follows every framework release. **Nothing is copied into `plugins/` unasked.** The set used to be seeded into every vault, and the cost, named at the time and now paid down, was that a framework fix never reached a copy already made: this workspace's own copies were measured a licence header to 283 lines behind, none of them edited on purpose. `guest/plugins/` is still not served at `/guest/` — one url per plugin, the vault's `/v/<enc>/plugin/…`, where the vault's file answers first and the framework's second, per FILE, so a `plugins/kanban/index.html` alone still gets the framework's `kanban.js` underneath it. **List `guest/plugins/` rather than trusting a roster written here**: a `<id>/index.html` is a page plugin, a `<id>.js` is a slot plugin, and adding either is adding a file. **What a person can READ is `docs/plugins/`** — the framework's set, mirrored into every vault in the background after the mount answers by `server/workspace/framework.ts`, written whole every time rather than filled so it cannot drift, ignored by the vault's history, and read by nothing that draws. **What they can CHANGE is an override**: a copy of a plugin, whole, from that mirror into `plugins/`; from then on it is theirs, pinned by choice, and deleting it is how they go back. **AND A COPY THAT IS ALREADY THERE IS LEFT THERE.** A vault seeded before this holds the old copies under `plugins/`, and they are overrides now — stale ones, drawing in place of the framework's — because the framework cannot tell a copy nobody edited from one somebody did without carrying every version it ever shipped, and it does not: that was a git-blob-hash sweep once, and it was taken out as a carve-out not worth its machinery. This is a BREAKING CHANGE, said as one: whoever owns the folder deletes the copies they did not mean to keep. Neither job is on the mount path, and `Host.settled(path)` is how a test waits for them.

**EVERY FRAMEWORK PLUGIN WEARS `biom-`, FILE AND ID ALIKE, AND A PAGE GOES ON SAYING THE BARE NAME.** `guest/plugins/biom-markdown.js` registers `biom-markdown`; `guest/plugins/biom-doc/index.html` is what `plugin: doc` falls back to. The reason is the same as the skills': a plugin a workspace wrote must never share a name with one the framework ships later — under bare names, the day the framework shipped a `flow.js` the workspace's `flow` was refused as its duplicate on every page, with nothing saying so. **A bare name is resolved nearest-first on BOTH sides of the wall, and that is what keeps every existing page and section true**: `resolve` in `guest/runtime/registry.js` answers the workspace's own `reveal` if one registered and the framework's `biom-reveal` otherwise, for `data-g-plugin`, `ctx.use` and a slot's part kind alike; `frameworkPlugin` in `server/domain/pages.ts` does the same for a page's document — the vault's `plugins/doc/` and then the framework's `biom-doc/`. `OURS` is the one spelling in each file and a test holds the two equal. A part kind is reserved to its file whichever name it wears: `markdown` to `plugins/markdown.js`, `biom-markdown` to `biom-markdown.js`, and a ```biom-html fence is a code sample exactly as a ```html one is. **Overriding the framework's plugin is a vault file under the PREFIXED name** — `plugins/biom-markdown.js` shadows `biom-markdown.js` by filename and nothing else enters the script for it; a vault `plugins/markdown.js` is a plugin of the workspace's OWN, which bare lookups reach first and which the framework's release can never refuse.

**A VAULT'S OWN SLOT PLUGIN LOADS, AND WHAT ANSWERS "WHICH PLUGINS DOES THIS VAULT HAVE" IS THE FOLDER UNION THE FRAMEWORK'S SET.** `GET /v/<enc>/plugin/` — the route that serves one plugin file, with nothing appended — is `pluginBundle` in `server/main.ts`: the framework's `*.js` MINUS every name the vault also has, then the vault's `plugins/*.js`, each in id order, so a vault `biom-markdown.js` shadows the framework's by name and the registry never sees two of one id, a vault `markdown.js` is the workspace's own and loads beside it, and the framework's go first so a vault plugin that `ctx.use`s one finds it registered. Each file is preceded by a comment naming it and its root and wrapped in its own function, so **a failure is reported as `plugins/<file> did not load: …` or `framework/<file> did not load: …` rather than as a slot saying `no plugin named "…" is registered`**, which reads as the page author's bug and is the plugin's. A source that does not PARSE is the case a `try` cannot catch, so each one is compiled on the server with `new Function` and a file that fails is replaced by the sentence saying so — one broken plugin is one broken plugin rather than a vault whose every page draws nothing. The client weaves **one** tag for it and **carries no list of plugin ids at all**; putting one back is the regression to watch for, because that list is exactly what made a workspace's own plugin unreachable. An absent or empty `plugins/` answers the framework's set alone and never a 404. **None of it is a `contracts/` edit**: a `plugin.list` kind or a field on `VaultInfo` were the alternatives and were rejected for being one. `plugins/<id>.js` is a slot plugin, `plugins/<id>/index.html` is a page plugin, and the filename alone says which.

**TWO THINGS A FILE IN A VAULT CANNOT SPELL, AND THE HOST SPELLS BOTH.** A plugin's document has no base to resolve a relative `src` against — the box is a `srcdoc` frame at an opaque origin — and it was written to disk long before anybody knew which folder it landed in, so it cannot name the vault route either. So `client/platform/document.js` takes the vault: the slot-plugin tags it weaves name `vaultBase(path) + "/plugin/"`, and a `<script data-g-src="biom-kanban/kanban.js">` in a plugin's own document becomes a real `src` under the same route as it weaves. **No file in a vault may name `/guest/`** — a path into an install directory, written into somebody's folder, is wrong the first time they move the application.

**THE PART KINDS ARE SPOKEN FOR BY THE FORMAT, and `shipped` is still a fact about provenance.** `markdown`, `html`, `table`, `child` and `grid` are not plugins the framework happens to ship: a slot's plugin is named by its part's `kind`, so a second file claiming one replaces the drawing of every slot of that kind in the workspace. The runtime holds those five from the moment it loads — the set is `PartKind` in `contracts/types.ts`, said again in `guest/runtime/registry.js` and held equal to it by a test — so the FIRST registration fills the reservation and every one after is refused in a sentence naming the reason. `document.currentScript` against `/guest/` still decides `shipped`, and what `/guest/` means now that nothing else is served from it is *the framework's own runtime*.

**This is not `kind:` coming back.** That key claimed a page was one of a closed set of things the host understood, and every one of them was a branch in the host. This one names a document, the host has no opinion about what that document does, and the set is open by construction.

**SECTIONS ARE THE DOC PLUGIN'S CONCEPT, not the page's.** A section is a div with its own HTML file and its own named slots; `contents` is an ordered list of them and the array IS the order. Three columns of prose is ONE section with three markdown slots. Nothing outside the doc plugin knows what a section is — child reconciliation, `section.order` and the whole section runtime are its, and a board has no sections at all. That is the freedom the model exists for: an html page is whatever an agent wrote, and it is not obliged to be a stack of anything.

**There is no edit mode, and nothing is drawn over the page.** A page is editable the moment it is drawn: click a paragraph and type. The SLOT under the caret shows its RAW markdown — the whole part, every block and the blank lines between them — while every other slot stays rendered, which is what keeps `{{name}}` a variable rather than the value it happened to resolve to, and why editing the rendered output was rejected outright. **A block is whatever the plugin says it is**: `def.blocks(source)` answers character ranges and the tag each one is drawn as, markdown.js reads both off markdown-it's token map, and the open slot holds one element per block of that block's own tag — so a heading's source is heading-sized with its `# ` showing, sized by the page's type scale rather than by anything copied, and typing `# ` in front of a paragraph makes it one as you type. **The chrome that used to sit beside that is gone**: no menu on a section's corner, no grip, no `+` at a seam, no drag of a section or a list item. A section's order is structure an agent writes, and rearranging it is a sentence you hand the agent; an overlay that is invisible until hovered was a mechanism serving a gesture nobody needed. **What the runtime does NOT ship is a section's own add and delete**: where those sit is that section's design, and the vault skills make drawing them a condition of the section being finished. `guest/runtime/edit.js` owns all of it and `.agents/skills/section-runtime-guide/` is the guide.

**So the authoring standard is a consequence rather than a taste: all TEXT is markdown, in `content.yaml`, behind a `data-g-part` slot, and a section's html file carries the visuals and the structure and none of the words.** A markdown part is the only region that opens under the caret, so **a word baked into an html file is a word nobody can ever edit** — the difference between a page that can be used and one that can only be looked at. Text inside an `<svg>` is the one exception, because it is part of a drawing. `skill/check.ts` WARNs on the rest as R56, and `vault/.agents/skills/biom-sections/SKILL.md` carries the rule, the block-level trap that comes with it, and the worked before/after; `vault/docs/sections.md` carries what a slot IS, for the person reading rather than writing.

**A slot's id is its key in `parts`.** A `Content` has no `name` of its own — the map already states it — which is why `section.write` names a page, a section AND a part. A bare string in `parts` is markdown, because prose is most of what a slot holds; a map is a full `Content`, so a slot takes a table or a child just as easily.

**`markdown.yaml` is the type scale, and it is a format rather than a stylesheet.** One at the vault root is the house scale every page inherits; one in a page's directory is that page's, merged over the house a property at a time. It exists because once almost every visible word is a markdown part, *how big is a heading* stops being one section's business and becomes the page's. It **cannot name a colour** (the palette owns colour, and there is no property for it), **cannot name a font** (`face:` takes a type ROLE), and **has no selectors** — which is what lets the checker report a line it does not understand and would let a control in the app drive it. A section's own `<style>` always wins, by cascade layer rather than by specificity, so the scale is a default and never a ceiling. Unknown lines are dropped rather than fatal: a typo in a type scale must not be what stops a document opening. `contracts/scale.ts` is the one walk the page reader, the design reader and the checker share.

**Resolution is mandatory and server-side.** `page.read` answers `DrawnSection[]`: every section's HTML loaded, every part resolved, every variable scope gathered. That is not an optimisation — the runtime that draws it lives in an opaque-origin frame and cannot `fetch`, so a part that named a file and expected the guest to load it would simply never draw. The one exception is code, which arrives as a classic `<script src>` from `/guest/`, `/vendor/` or the vault's own `/plugin/`.

**The shipped default section is a file, not a branch.** A section that names no `data` draws with `guest/sections/default.html` — one centred slot named `body` — and `DrawnSection.fallback` says so. A default living in the runtime would be the one shape nothing else could reach, and "the document" would be privileged again, which is exactly what the old doc render kept collapsing into. `server/main.ts` reads it once and hands the string to `makePages` and `makeDesign`, because nothing may import `guest/` and both readers must draw the same default.

**`content.yaml` is required, and an old vault refuses rather than half-opening.** A page directory without one is not a page and `page.read` answers `not_found`. A workspace still carrying `kind:`, `render:`, `order:`, `parent:` or `page:` is an older format; this server reads format 4 and `server/workspace/migrate.ts` refuses anything else by name, before a single module that could read a page is constructed.

**Format 3 is the one that converts, and the refusal names its tool.** Nothing about those pages changed — only what they say about themselves — so `tools/migrate-format-4.ts` adds `plugin: doc` after each page's `name:` and nothing else, editing text rather than going through the codec so the diff is one line per page. **Formats 1 and 2 still have no converter and never will**: a section IS its markup, and the markup lived in the render layer rather than in the vault, so a conversion could only flatten every page into the default section and call it migrated.

**Every page renders itself as markdown, and the page is what computes it.** `<vault>/_markdown/` holds one `.md` per page, derived and read-only, with a `AGENTS.md` inside saying so — it exists because a brain reads markdown files and a workspace whose prose lives in `content.yaml` is invisible to one. The box runs the page's code, so it is the only half that knows what a board says in words; it cannot write a file, so it says the words over `page.projection` and the host writes them. A doc page can also be projected server-side from pure data, which is what fills a mirror on mount and what the migration tool uses so no page starts blank. `server/domain/mirror.ts` owns the folder and `contracts/projection.ts` the rule, with `guest/runtime/project.js` a hand copy held byte-equal by a test. **A RESERVED ID IS NOT MIRRORED AND IS NOT ASKED TO BE**: `_markdown/` is keyed by page id and `@` is outside a path segment's grammar, so the mirror refuses such an id BY NAME — for a caller that meant it. The runtime never means it, because it projects every page it draws, so `sendProjection` in `guest/runtime/boot.js` returns on an id starting `@` rather than spending a refusal; without that, opening the design doc printed a stack trace on the server and a line in the box every time.

**The vault is chosen in the UI, and the choice outlives the process.** `VAULT` in the environment wins on first boot; otherwise the last one opened; **otherwise nothing at all.** The memory is one JSON file in the per-user data directory (override with `VAULTS`, which the tests need) — it is ABOUT vaults, so it cannot live inside one.

**STARTING UP SURVIVES EVERY BAD STATE A FOLDER CAN BE IN, and each one is one plain sentence and the picker.** The owner decided this on 2026-09-14: *"opening an old vault shouldn't be a crash; we should be a lot more fault tolerant than this."* The application trusted whatever it remembered, and measured against a real run that was three dead processes and two silent writes — a remembered vault that had become a file died on `EEXIST` out of `mkdir`, one whose folder could not be read died on `SQLITE_CANTOPEN`, a `workspace.db` that was not a database died on `SQLITE_NOTADB`, a DELETED one was recreated by `initVault`'s `mkdir -p` and seeded from scratch so the program opened an empty workspace wearing the lost one's name, and one on a volume that was not mounted had its whole missing path created inside the empty mount point. **Three pieces answer all of it and each is the only place its question is asked.** `usable` in `server/workspace/vault.ts` is the one gate every mount goes through — there, a directory, readable, WRITABLE, and not holding a `workspace.db` whose first sixteen bytes are not SQLite's header; it writes nothing and repairs nothing, because a database that will not open holds the rows and a framework that moved it aside to get itself started is the one outcome worse than refusing. `bootVault` beside it is the one place a bad REMEMBERED entry is decided, and **the asymmetry is the rule**: `VAULT=` is trusted and created because somebody typed it on this launch, a remembered path is checked because it is a claim about the past and the past goes stale. `Host.trouble` in `server/main.ts` is the guard around the boot mount, so a failure nobody has thought of yet — a locked database, a format gate, a disk that fills — is still a sentence rather than a top-level await taking the process with it. **A host is always built**, `makeHost` never rejects, and what a bad folder produces is exactly a first launch plus a reason. `tests/bad-startup.test.ts` walks every state named above.

**AND THE TAB LANDS ON THE PICKER, WITH THE SENTENCE ABOVE IT.** A request naming a folder that will not open used to be a bare 404 with a plain-text body, on the reasoning that a stale url should fall back to the picker rather than show a broken page — which is right about where the tab should end up and wrong about what it should say. **Nothing on the client reads the status**: the transport treats a body that is not an envelope as a transport fault, so what a person actually saw was *the server answered 404 with something that was not a response*, naming neither their folder nor what was wrong with it. **A DATABASE WRITTEN BY A NEWER BUILD REFUSES, on `migrate.ts`'s own argument.** `_meta.format` has been written since the registry existed and was never read, which made it a note to a future maintainer rather than a gate — and the two statements under it widen `_tables` in place and reconcile the registry against what is physically there, which against a schema this build has never seen is a guess acting on somebody's rows. `checkDbFormat` in `server/domain/tables.ts` runs after the `CREATE TABLE IF NOT EXISTS` sweep (which does nothing to a database that already has them) and before every write, and only the FUTURE is refused: an older number is what a migration is for and there has not been one yet.

**A NEW WORKSPACE IS A PARENT FOLDER AND A TYPED NAME.** Not a path field with a default in it, and no invented `~/Biom`: a prefilled absolute path is a decision made for somebody about a folder they have not looked at, and the one thing a person knows on a first launch is where they keep their own work. `creatable` in `server/workspace/vault.ts` is the whole of the decision and none of the act — the name rule, the ancestor walk, and a sentence per row of the collision table — and `createVault` is the act. **The walk runs from the chosen parent to the filesystem root**, refusing if ANY level is already a workspace: a parent-only check passes on a folder four levels inside somebody's page tree, and what comes back from that is two databases, two mirrors and two git repositories over one set of files. Siblings are not ancestry, so a folder holding three workspaces is fine. **`vault.create` carries a parent and a name and never a joined path**, all the way from the button to `mkdir`: given one string, a name with a separator in it makes a folder somewhere nobody chose. The picker's Create button is enabled by the same expression that writes the refusal under the name field — `make.disabled = why !== null` — because two opinions about one question are one opinion that gets forgotten. The server checks the same things again and more; the client's half is so the answer arrives while somebody is typing.

**NOTHING IS WRITTEN BESIDE THE INSTALL, and those two files are the only two it ever wanted to write.** Both were under this directory — the default vault at `workspace/`, the list at `.vaults.json` — which makes a program in `/Applications` or `/usr/local/bin` unable to run at all, and a program that *can* write there one that has just seeded a workspace into the middle of somebody's source tree. `dataHome()` in `server/workspace/vault.ts` is the one place the folder is worked out: XDG on Linux, `Application Support` on macOS, `%LOCALAPPDATA%` on Windows, one directory rather than a config half and a data half. Everything else the server reads — `vault/`, `skill/`, `client/`, `guest/`, `vendor/` — stays relative to the install and stays read-only, which is what LET a compile replace it wholesale — it does now, and the carried manifest below is how.

**THE MAKEFILE NAMES NO VAULT, and `fresh` deletes only inside the data directory.** It used to default `VAULT` to a folder beside the checkout, so every unqualified `make dev` served whatever workspace happened to be there — and `fresh`, whose help line promises a throwaway seeded folder, was `rm -rf` of it. Serving a particular workspace is now explicit: `VAULT=` on the command line. `tools/fresh.ts` carries the confinement, refuses anything outside by name and exits non-zero.

**`dev` and `up` fetch nothing.** `install` is for `types`, `browser`, `test` and `app` — TypeScript, Playwright, the type packages, and Electron with its packager — and the server runs on none of it: the only bare specifiers under `server/`, `client/`, `guest/` and `contracts/` are `markdown-it` and `yaml`, both vendored and resolved through `paths`. **`make app` IS ONE LINE CALLING `tools/app.ts`, and `bun run app` runs the same script.** A Windows shell has no make, so a build that lived in a recipe would be a build one of the three systems could not run — which is the whole reason it left the Makefile rather than a preference about where build logic lives. It generates the embedded-file manifest, compiles the server for one target, packages the Electron bundle around it, and INSTALLS it. Everything it writes inside the repository is under the gitignored `dist/`.

**THE BUILD ENDS WITH THE DESKTOP FINDING IT, and overwrite is the rule.** A bundle under `dist/out/` is a folder nothing on the machine knows about, and on Wayland a window whose application has no installed `.desktop` file cannot even be given its icon — the compositor matches the window's app id against an entry and there is none. So `tools/install.ts` is `make app`'s last step: on Linux the bundle goes to `<data home>/app`, beside the data the application already keeps, with a `biom.desktop` entry and the icon in the hicolor theme at every size `tools/icon.ts` derives; on macOS `Biom.app` goes to `~/Applications`; on Windows the folder goes under `%LOCALAPPDATA%\Programs\` with a Start menu shortcut. **A rerun replaces all of it without asking** — the developer's case is a rebuild, and a prompt is the wrong answer to it. The copy is staged in a sibling and swapped in by rename, so an interrupted install leaves the working application where it was. `make uninstall` removes exactly what the plan says was written and nothing above it; **the vaults are never in that list**. `app.setDesktopName` in `app/main.js` is the shell's half of the Wayland match, and the entry's `StartupWMClass` is the other.

**`installPlan()` IS PURE AND THAT IS WHAT MAKES THE OTHER TWO SYSTEMS CHECKABLE.** Given a platform, a home and a data directory it answers every path that will be written and every path that would be removed, touching no disk and joining paths the TARGET's way rather than this machine's — so `tests/install.test.ts` holds the macOS and Windows arms from Linux, and the real-install test runs into a temporary `XDG_DATA_HOME` rather than the machine's own. **A running instance is fine on Linux and macOS and is not on Windows**: there the process holds its old inode and goes on working, here the files are locked, so the install says so and stops.

**`--no-install` IS WHAT CI PASSES AND THE ONLY THING THAT SHOULD.** A runner has no desktop and is deleted a minute later; the flag stops the build at the bundle, which is what `ci.yml`'s pass condition looks for. A build for a target that is not this machine stops there too.

**THE COMPILED SERVER CARRIES EVERY FILE IT SERVES, because a binary has no directory beside it.** `tools/app.ts` walks `client/`, `guest/`, `vendor/`, `vault/`, `skill/` and `contracts/` — walked rather than listed, because a list of a hundred files is wrong the first time anybody adds one — copies each under `dist/files/` with a `.bin` suffix, and writes `dist/embedded.ts`: one `import … with { type: "file" }` per file and a map from the framework-relative path to it. **`contracts/` is in that list and is not optional**: every client module reaches `wire.js` by a relative path that resolves at `/contracts/`, so a binary without it serves an application that cannot boot.

**Two things about that manifest are load-bearing and both were bought.** The COPY is what stops a specifier collision — a module specifier is one cache key per process, so importing `client/store/ui.js` as a file and then as a module hands the second importer the first one's module, and five test files stopped loading with a syntax error naming an export that is plainly there. The `.bin` SUFFIX is what stops `tsc` following the literal import into a hundred carried files, `vendor/`'s minified bundles among them. The import has to stay a literal, because `bun build --compile` bundles what it can see and a computed specifier is a file it silently leaves out.

**The composition root asks whether there is a directory beside the program, not an environment variable.** `server/platform/embedded.ts` is a read-only `Files` over the carried map; `main.ts` hands it to the seeder in place of `makeFiles`, which is why `server/workspace/presets.ts` is untouched — it is handed `Files` and walks what it is given, so a swap really is one line in a root. **PORT 0 AND A PER-LAUNCH TOKEN, IN THE BUILT APPLICATION AND NOWHERE ELSE.** The compiled server asks for port 0, mints one random token, and prints `biom ready {"port":…,"token":…}` on stdout before anything else it says; the Electron shell reads that one line and only then opens a window at that address. A development server keeps 4400 and mints nothing, because it is opened by somebody typing a url. **The token is an ADDRESS, not a message**: it rides on the request the way the vault prefix does, `contracts/` has no type for it, and the client-side half is `client/transport/http.js`, the two lines in `client/boot.js` that read it out of the window's own url, and **every address the client itself builds** — which is the part that was missed. **A QUERY IS REWRITTEN WHOLE, so anything that writes one drops the token**: `boot.js` keeps the rest of the query when it writes the folder in, and `hrefFor` in `client/views/vault.js` does the same for every workspace this application links to, because `"?vault=" + path` sent the picker to a document with no token and a server that answered 401 to every call it made. **It guards `API_ROUTE` and nothing else** — the box has an opaque origin and loads fonts, `/vendor/` scripts and the vault's own plugins by URL with no way to set a header, so the framework's read-only static roots stay open. `/asset/` and `/plugin/` do serve the person's own folder and are the unresolved half, and `EVENTS_ROUTE` is a third that could carry the token and does not yet — what it leaks is that a folder is being written to, because the event carries no payload at all. **The query cannot settle them**: a page in the box writes `<img src="kitchen.jpg">` and the browser resolves it against the `<base href>` `client/boot.js` builds, and relative resolution REPLACES the base's query — so the token would have to be a path SEGMENT, which is an edit to `vaultBase` in `contracts/wire.js` and waits for a barrier. `tokenOk` in `server/main.ts` carries the whole of it.

**The shell spawns, reads, opens and quits, and is deliberately nothing else.** `app/main.js` starts the compiled server, reads the port and the token off that line, opens the window, quits the server when the window closes and says so in the window when the server dies. **AND THE SERVER NEVER OUTLIVES IT, including when the shell does not get to quit anything.** A main process that ABORTS runs no handler of ours, and what that left on the owner's machine was a `biom-server` holding a port and a workspace open with nothing on screen to say so — twice, after the font crash below. So the server is spawned with a PIPE as its stdin and `BIOM_SHELL=1` in its environment, and `exitWhenTheParentGoes()` in `server/main.ts` exits the moment that pipe reaches end of file. **Nothing is ever written down it**: its only message is its own closing, which the operating system performs when the process holding the write end dies, however it dies. **Stdin rather than a parent pid** because it is the only one of the two that is the same thing on all three platforms — `getppid()` is not on Windows, `PR_SET_PDEATHSIG` is Linux's alone, and polling a pid is wrong the moment the number is reused. **The marker is what makes it safe**: a server started any other way — `make dev`, a binary run from a terminal, a launcher pointing stdin at `/dev/null` — sets no marker, watches nothing and is the program it was. The name is spelled in `app/main.js` and `server/main.ts` and in no third place. Single instance is Electron's own lock and is per application rather than per vault — the server already holds several vaults at once and addresses them by path, so opening a different folder is a navigation inside the one window. A shell that knew what a vault was would be a second place the product is described.
**THERE IS NO MENU BAR, and the removal happens before any window exists.** Electron's default application menu is File, Edit, View, Window, Help — a developer's menu, carrying a Reload and a Toggle Developer Tools — and it describes a program this one is not: the window is one page and everything in this application is on that page. `unmenu()` in `app/main.js` is called first thing inside `whenReady`, ahead of the spawn, because a menu replaced after a window is open is a menu somebody sees flicker. **The window keeps no title bar either** — see below. **macOS is the exception and it is not a preference**: copy, paste, select all and undo inside a web page are Chromium's on Linux and Windows and the MENU'S on macOS, so a null application menu there is a window where ⌘C does nothing — macOS therefore gets a menu holding the edit roles and nothing else, and **it is shown**: an Edit menu marked `visible: false` registers no accelerator on macOS — measured with a real ⌘V, which pasted nothing, into the Agent Terminal or anywhere else — while the same menu shown works. It draws no bar of ours, because macOS puts it in the menu bar at the top of the screen beside the application menu it draws anyway. macOS draws its own application menu whatever is set here and no program can remove that one. **Full screen is on the bar and on F11**: the bar's button is the discoverable way and `fullscreenOnF11()` keeps the key every browser already trained people to reach for, on Linux and Windows through `before-input-event`; macOS keeps its native full-screen role on the hidden menu beside the edit roles, because F11 there is the desktop's own key. **THE APPLICATION DRAWS ITS OWN TITLE BAR, and the controls on it are ours on every desktop.** The owner decided this on 2026-09-14, the way VS Code, Discord and Slack already do it on Linux, and the reason is that the desktop's bar is not the same bar twice: GNOME hides the maximise button by default, offers no full-screen button at all, and puts close on whichever side its settings say. **The option that removes it is different on each platform and none of the three is a preference** — `chromeOf()` in `app/main.js`: `titleBarStyle: "hidden"` on Windows, which hides the bar and KEEPS the native frame under it (resize edges, Aero Snap, the shadow — `frame: false` there throws all three away); `frame: false` on Linux, where `titleBarStyle` is not implemented at all and Electron keeps the resize edges itself; `titleBarStyle: "hiddenInset"` on macOS, so the traffic lights stay, native, inset into our bar. **The client draws the bar** — `client/shell/shell.js`, dressed in `chrome.css` — with the mark and the workspace's name on the left and minimise, maximise/restore, full screen and close on the right, in the product's own type and tokens, the strip a `-webkit-app-region: drag` region with the controls taking it back as `no-drag`, and a double-click on it maximising because on Linux there is no window manager left to do that. **On macOS three of the four are not drawn**: the lights ARE close, minimise and zoom, and the bar leaves them the room `inset` names — full screen is drawn there too, because the green light is zoom-or-full-screen depending on a modifier. The maximise icon follows the WINDOW rather than the button, so F11, a drag to the top of the screen and a tiling manager all flip it. **F11 is kept**: the button is the discoverable way and F11 is the one every browser already trained people to reach for. **In a browser none of it is built** — no `windowControls`, no `.framed`, no row in the grid — so `make dev` in a tab is exactly the page it was.


**A WINDOW THAT NEVER DRAWS IS A SENTENCE, NOT A CORE DUMP.** Measured on the machine this was found on: `~/.cache/fontconfig` held caches written by two different fontconfig versions — a host and a toolbox sharing one home directory — so Chromium was handed a font list it could not use, aborted with `FATAL: SkFontMgr_FontConfigInterface.cpp:163 Not implemented`, and dumped core. What a person saw was nothing at all: no window, no message, an application that appeared not to start. So `app/main.js` watches the ONE gap where a death means that — between asking for the first page and `did-finish-load` — on `render-process-gone`, `child-process-gone` and a `FIRST_DRAW_MS` bound for the case where nothing dies and nothing draws either. It prints one plain sentence to stderr, shows a native `dialog.showErrorBox` naming the likely cause and, on Linux, the fix (`rm -rf ~/.cache/fontconfig && fc-cache -f`), then stops the server and exits non-zero. **THAT PARTICULAR CAUSE IS NOW SIDESTEPPED RATHER THAN ONLY EXPLAINED, because a cleanup command on somebody's own machine is not a fix a stranger will know to run.** `ownFontCache()` in `app/main.js` gives the launch that opens the window a font cache of the APPLICATION's own — `<dataHome>/cache`, beside the vault list, `dataHome()` mirrored for the shell in `app/data.js` and held equal to the server's by a test — so the window's Chromium reads only files one fontconfig wrote, the one inside this bundle. **IT RESTARTS THE PROGRAM, and that is measured rather than chosen**: Chromium has already read fontconfig's cache by the time `app/main.js` runs, so setting `process.env.XDG_CACHE_HOME` there is not enough — a bundle that did only that wrote its `fontconfig/` into the caller's cache directory and put nothing but shader caches in ours. The variable has to be in the environment the process STARTS with, so the shell calls `process.execve` with it and `BIOM_OWN_CACHE=1`, which REPLACES this image: same pid, same standard streams, same command line, so a desktop launcher, `xvfb-run`, a script waiting on it and the end-to-end suite all keep the program they started. **A spawned child supervised by its parent was tried and is worse in a way that is easy to miss**: the first process has already taken whatever its command line asked for, so `--remote-debugging-port` ends up bound by a process with no window in it and the suite finds no target. **It never refuses to start**: no `execve` on the runtime, a data directory that cannot be made, a replacement that throws — each is one line on stderr and the launch every version before this one made. **What it cannot avoid** is that the image before the replacement has already read the person's cache and left a dozen or so files of its own version in it; what it buys is that the image that opens the window reads none of it. Linux only, because fontconfig is and because `execve` is not on Windows. **Nothing of the person's is repaired**: no `FONTCONFIG_PATH`, no font flag, nothing cleared and nothing rewritten — `~/.cache/fontconfig` is theirs and every other program on the machine goes on reading it. **The dialog stays** because a window can fail to draw for more reasons than this one. **What it cannot catch is an abort in Chromium's own BROWSER process**, which is this process, and no handler of ours runs after that; the arms cover the children. After the first draw none of it applies — a renderer that dies later is an ordinary crash.

**ONE PICTURE OF THE LOGO IS COMMITTED, AND THE BUNDLE'S ICONS ARE GENERATED FROM IT.** `app/icon.png` is the one committed picture of the mark, and it lives inside this repository rather than being reached for somewhere above it — nothing here may name a path outside this directory, because this directory is the whole of what is published. It is in `SHELL_FILES`, so it lands in the staging directory, and `app/main.js` reads it from beside itself as the WINDOW's icon: the title bar and the task bar on Linux and Windows. The BUNDLE's icon is a different thing — macOS wants `.icns`, Windows wants `.ico` — so `tools/app.ts` writes `dist/icon.icns` and `dist/icon.ico` on the way past and hands the packager the path WITHOUT an extension, which is the form it appends to. **Neither generated file is committed**, because a generated icon in the repository is a second copy of the logo that goes stale the day somebody redraws the first. **`tools/icon.ts` writes both containers itself**: `sips`, `icotool` and Pillow are three dependencies on three systems, and a build that needs an interpreter it did not declare is a build that works on the machine it was written on. An ICO is a directory in front of a run of whole PNGs and an ICNS is the same idea with a four-letter type per entry — what is not trivial is that an ICO entry records its size in ONE BYTE, so 512 cannot be spelled and the picture has to be made smaller first, which is why there is a PNG decoder and a box filter in that file. The decoder is 8-bit RGBA, non-interlaced, and refuses anything else by name. **Linux takes neither container**: `@electron/packager` writes no `.desktop` file, so the Linux icon is the window's. **It is also the mark in our own title bar**: `app/` is not a served directory, so `logoUrl()` in `app/main.js` reads that same file once and hands it over the bridge as a `data:` URL — one picture of the logo, three jobs, and no second copy under `client/` to go stale.

**THE BRIDGE IS FOUR THINGS AND THE LIST IS CLOSED.** `app/preload.js` exposes `window.biomShell` carrying `chooseFolder()` — the operating system's folder dialog, answering one absolute path or null for a cancel — `logo()`, the committed mark as a `data:` URL, `capturePage()`, the drawn page read out of the box by the main process for Share (the one thing a page in this window cannot read for itself, and the paragraph on the seventh contracts edit says why it is here), and `windowControls`, which is this window: `minimize`, `toggleMaximize`, `toggleFullScreen`, `close`, a `state()` reader, an `onChange` subscription, an `onClosing` subscription (the window was asked to close over a live automation — the eighth contracts edit's paragraph has the hold), and the two facts a page cannot work out for itself (`lights`, whether the platform draws close/minimise/zoom itself, and `inset`, how much room to leave them). Each act is one `ipcMain.handle` channel; `onChange` rides the one channel the main process pushes on. `contextIsolation` is on, `nodeIntegration` off, Electron's default sandbox. **It grew from one function because the application draws its own title bar** — a page that draws the window's controls has to be able to work them, and minimising a window is as far outside a web page's reach as an absolute path is. Nothing else crosses: no node, no `fs`, no `shell`, no `ipcRenderer` handed over — the object itself on the world is every channel the main process ever answers — and no channel takes a window id, because there is one window and an id would be a channel a page could aim elsewhere. **The picker and the bar both treat ABSENCE as a supported state rather than a fault** — no `biomShell` is a browser, so the picker draws the served Browse listing and the shell draws no bar at all, which is what keeps `make dev` and the built application one program. `tests/app.test.ts` holds the surface to that exact list of names, holds every channel spelled in both files and in no third place, and holds the staging list to the files `tools/app.ts` copies.

**One answer to "is this path inside that one": `within` in `server/platform/files.ts`.** It was written three times — the vault's own path guard, `under()` serving a static file, and the check in front of `fresh`'s `rm -rf` — and a containment written three times is three chances to write the one that answers yes for `/srv/clientele` when it was asked about `/srv/client`. Both sides are resolved and then compared as paths; `strict` is the difference between *inside the vault* and *a folder I may delete*.

**`main.ts` joins paths with `node:path` and derives its own directory with `fileURLToPath`.** `.pathname` off a `file:` URL percent-encodes, so an install under a path with a space in it served nothing and said nothing; on Windows it is `/C:/…`, which no filesystem call takes. **The `${a}/${b}` strings in `files.ts`, `presets.ts` and `vault.ts` are NOT the same thing and must stay exactly as they are** — those are vault-relative logical paths and page ids, forward-slashed by the format, and `path.join` there would put a backslash into a page id and into a mirror filename on Windows.

**A vault whose `git init` failed still works, and the UI must never claim otherwise.** Pages read and write, the mirror rebuilds, the seed lands, and the vault gets its `.gitignore` — the condition for writing that is *this folder is new*, not *a repo was made here*, because the alternative leaves a machine with no git holding a vault that tracks `workspace.db` the day git arrives. The only thing missing is undo, and the person is entitled to know: **`VaultInfo.history` carries the fact, and only the bad news is ever said.** A vault that is keeping versions says nothing, because there is nothing to act on; one that is not gets a statement on the status strip, which is the one surface that says it. Silence is also what an unread `vaultInfo` gets, because an absent fact is not a negative one. `hasHistory` in `server/platform/files.ts` is the answer — beside `commit()` and `initVault()`, which turn on the same `.git`-on-disk check and must never diverge from it — `infoOf` in `server/workspace/vault.ts` is where it is read, and the boot line still says it once to a terminal.

**Several vaults are open at once, and which one a request means is in its URL.** `POST /v/<url-encoded-absolute-path>/api/call`, so the browser address is `?vault=/some/folder#/page/home` and a tab visibly says which workspace it is. `main.ts` keeps a map of path → the promise of its mount; **it holds promises rather than mounts**, because two requests for one folder arriving together must share a mount — two would be two database handles on one file and two seeders writing one tree. Nothing is ever evicted: a handle is cheap and a cache with a lifetime is a bug with a schedule.

**The vault is an ADDRESS, not a message, and that is why it is not on the envelope.** `ApiRequest` is a strict superset of `HostRequest`, so a `vault` field there is a field an artifact could set — and an artifact has no business knowing the workspace is a folder, let alone naming a different one. Prefixing the route left the tagged union untouched, so it still survives the move to postMessage, where the port *is* the vault. `vaultBase` and `vaultOf` in `contracts/wire.js` are the one spelling both sides read.

**The path is the key, and a short id was rejected.** The remembered list caps its length, so an id resolved through it can age out from under a tab that bookmarked it; a path resolves for as long as the folder is there, and it is legible in the address bar.

**A request may name no folder, and that is a state rather than an error.** Unprefixed `/api/call` answers `vault.browse`, `vault.open` and `vault.recent` — the three kinds that are about vaults rather than in one — and refuses everything else, `vault.info` included: *which folder is this* has no answer when the request did not say, and the most recently opened one is somebody else's tab. It is what makes the picker reachable before anything has been chosen. **AND A FOLDER THAT WILL NOT MOUNT ANSWERS THE SAME FOUR KINDS**, which is not a courtesy: `deps(path)` used to REJECT, and the route turned that into a refusal of everything the tab asked for — so a window addressed at a workspace that would not open drew the picker and then watched the picker's own three reads fail down the same prefixed route, leaving the one screen that could fix the problem unable to list a folder or offer a recent one. Those kinds never needed the mount. Everything that genuinely does need the folder refuses with the MOUNT'S OWN sentence, so whichever call a screen makes first, it gets the same words.

**One tab is one folder, for as long as it exists.** The vault is settled in `boot.js` before a single module is constructed, and nothing below can move it — so opening another folder is a NAVIGATION, not a mutation. `openVault` now only checks that a folder can be a workspace (which is why the picker still calls it: a refusal has to be readable on that screen) and the picker then goes there. A store that cannot switch cannot be caught half-switched, which is what the three deleted tests in `store.test.js` used to guard by hand.

**A FILE CHANGING ON DISK IS A REASON TO PRESS RELOAD, AND THE SERVER PRESSES IT.** `server/platform/watch.ts` watches a mounted vault's authored input — `fs.watch`, recursive on macOS and Windows, one watch per DIRECTORY on Linux, because a watch on a file is a watch on an inode and an editor that saves by replacing leaves it watching nothing. The watched inputs and the exclusions are one list each beside the watcher; `mirror.ts`'s `pageAt` is what turns a changed path into a page id, using the `SEGMENT` rule it already carries because the vault root is also somebody's Obsidian folder. A burst is coalesced, the mirror is refreshed through the `follow` the API layer already calls — and through `drop` beside it, because `project` returns on a page it cannot read, so a page deleted from outside would otherwise keep a markdown file about nothing — and one event goes out over `GET /v/<vault>/events` — `EVENTS_ROUTE` in `contracts/wire.js`, because both tiers read one spelling of a route from there — served from `main.ts` and not from `routes.ts`, whose whole contract is one request in and one response out. The client re-runs `doReload`, which is the function the button calls: there is no hot patch, no diff on the wire and no new thing a page can say. **The event is not a wire kind** — a page never opens a stream and the box never learns the feature exists. **The reader's place survives the teardown**: the box scrolls inside itself and the host cannot read where to, so the shim reports it as a `position` notice, the mount keeps the latest, `doReload` says `frameHost.keep` before it reloads, and the new realm is handed it back as a `place` event on its `ready` — clamped in the box to whatever the page is now, applied instantly and at most twice, never on a loop. `boundary-guide` §3 is the mechanism; a page navigated to still starts at the top, because nothing but a redraw says `keep`.

**THE APP'S OWN WRITES ARE SUPPRESSED BY CONTENT HASH, and nothing else would do.** A write through the app lands in `pages/` and looks exactly like an agent's, so `Seen` in `files.ts` keeps, per mounted vault, the hash of what this process last wrote into or last read out of every file. Equal to the baseline, the notification is dropped and the baseline is unchanged; different, the baseline moves and the page redraws. A reread that does not parse — the middle of somebody else's save — leaves the drawn page alone AND leaves the baseline where it was, so the completed write reads as changed on the next notification. A timestamp window would be a guess about how slow the disk is and a path note would be a promise about ordering; a hash is the content.

**Which means EVERY VERDICT IN A BURST IS TAKEN BEFORE ANY PROJECTION RUNS, and it is the one ordering in `settle` worth reading twice.** The baseline moves on a READ as well as on a write, and projecting a page reads: a parent lists its children, so re-projecting one reads every child's `content.yaml`. Interleaved, the first of two siblings written together rebaselines the second before it has been considered, and the second's markdown is never written. A departure is asked of DISK for the same reason — the baseline is keyed by file and never by a bare directory, and a directory is all the notification a departing page gets.

**DISK WINS, AND THE ONE THING THAT REQUIRES IS WRITTEN BESIDE `SAVE_AFTER`.** When the watcher fires the page redraws from disk, the slot under the caret included, and a pending debounced save belonging to the redrawn editor is dropped rather than written. That is free on one path and only that path: an automatic redraw goes through `reloadPage`, which tears the frame down, and a 350 ms timer in a realm that has gone does not fire. **A cheaper redraw written to stop the flicker would reuse the frame and leave that timer armed**, and the person's stale text would land over the agent's — which is the exact failure the rule exists to prevent, and it is invisible until it happens.

**THE WATCHER'S LIFETIME IS THE STREAM'S, not the mount's.** Mounting does not unmount and nothing is ever evicted from the registry, so there is no moment at which a vault closes and no event to hang a release on. The subscriber count is the reading the code can actually offer: the watch starts on the first stream for that vault and is released on the last — which makes the requirement testable, where *release on close* would be a promise nothing can keep.

**`assets/` is a root sibling of `pages/`, served and never parsed.** `/v/<vault>/asset/<rel>` is one of only two routes that resolve inside a vault — the other is `/v/<vault>/plugin/<rel>`, which serves this workspace's own `plugins/` to the box as classic scripts — and everything else the client fetches is the framework's own, so a module keeps one URL whichever folder you are looking at. A picture is usually wanted on more than one page, which is why it is not a folder inside one. Keep it distinct from the per-page `_assets/` that `pageFile()` accepts for a section's or an `html` slot's `data`.

**Only an empty folder gets seeded, and this rule was bought.** A folder holding anything at all that is not already a workspace belongs to whoever put it there, so `open` refuses it — a dotfile counts, because `.DS_Store` means a person has been there and guessing which hidden files are ignorable is how a rule like this rots. `check` deliberately does not enforce it: browsing has to walk through non-empty folders to reach an empty one. **The framework was once pointed at the repo that builds it** — `initVault` found a `.git`, correctly declined to create one, then committed into it anyway, putting twelve commits of workspace onto `main` along with every untracked file in the tree. Nothing refused, because nothing was ever asked whether the folder was free. The refusal carries the domain's own sentence through the API rather than a flattened one, because a user who cannot tell *why* reads the picker as broken. **Creating one says the same thing one step earlier**: `creatable` refuses a name that is already a folder with anything in it, before the folder is made rather than after. **And `openable` now walks the ancestry too**, on `creatable`'s own rule and for `creatable`'s own reason: `<vault>/pages/home/children/Notes` is not empty, so *pick an empty one, or one that already holds a workspace* was true and useless — it invites somebody who has opened their own page tree to make a SECOND workspace inside the first. It names the ancestor, which is the same exception to the no-paths rule the create refusals take: the whole point of a walk is that what it found is somewhere the person did not look.

**A new vault is empty: the root page and nothing else.** Seeding somebody's folder with invented pages about a trade business was noise they had to delete before they could start. What still seeds is furniture rather than content — `design/`, `base/`, `theme.json` and `INSTRUCTIONS.md`, and then the root page; `plugins/` is NOT seeded, because the framework's plugins are the rung under the vault's rather than a copy inside it, and `AGENTS.md`, `docs/` and `.agents/skills/` are not seeded but REWRITTEN, because they are the framework's. **The root is a page that DRAWS ITSELF**: `ensureRoot` writes `guest/pages/welcome.html` into its directory as the page's own `index.html`, and the words beside it as the page's own top-level slots — `ROOT_WORDS` in `server/domain/pages.ts`, where the key IS the part, so every sentence on it opens under the caret and writes itself back. It used to be a `doc` page carrying a format lesson — what a `content.yaml` is, New page, Modify page, Reload — given to somebody who has not yet seen a page — and naming Modify page, a panel that no longer exists. What it says now is the one step to take, the folder to take it in, what this is for, and a set of things that may be asked for; the shape that carries it is a band bleeding the full width of the canvas over one of the brand's own risograph prints, which is not a shape the doc plugin's frame can make. **It is written for somebody technical building something for themselves**, and an ask is TWO BLOCKS of one markdown item — the short line it is known by, and under it a real prompt to paste into an agent, with a Copy of its own read off the DRAWN item. A parallel `prompts` list was rejected: the runtime draws a list as one region per item, so a second list would be a second set of regions the grid could not interleave and the page's own add would grow one and not the other. **One module per ask, and a test holds the two counts equal.** **The first thing it says to do is open the design doc**, through a `[[@design|Design]]` wikilink in the words — which is the one page no snapshot holds, so `resolveLink` and `open` in `client/bridge/bridge.js` each name the reserved id; that is a client change and no barrier. **The print travels inside the markup as a data url**, because `Files` reads and writes utf-8 and a picture that ships with a seeded page has to be text. **The page names the folder and asks rather than being told**: `biom.vault()`, read where the page is drawn, so it survives the workspace being moved — a path seeded into the document would be wrong the first time and wrong silently. The markup is read by the composition root and handed down, exactly as `DEFAULT_SECTION_FILE` is and for the same reason: it lives in `guest/` and nothing under `server/` may import it. **It is seeded after `INSTRUCTIONS.md`** and the guide lands a moment later off the mount path, and it is written only when there is no root, so an existing vault's root is never touched — and the copy in the page directory is the person's, to restyle or delete with the page. **Every instruction in it must be true of the build**: it once said to press Reload and no longer does, because the server watches the folder — and when the loop changes again, those words change in the same change. There is still no catalogue — it went with the render layer — so filling a vault is asking an agent, which is exactly what the root now says to do. Every write the seeder makes is additive file by file and never overwrites, so a vault made before a base block existed gains it on the next start while anything edited stays edited. That is a property of each write, not a gate around them: there is no longer a "has this been used" check to get wrong. The guide, the docs and the skills are NOT the seeder's — see below.

**The vault carries its own `AGENTS.md`, `docs/` and `.agents/skills/`, because the folder is what an agent is pointed at — and `docs/` because it is also somebody's folder.** A vault with no guide is yaml and html that nothing explains, and the format guide living in this repo reaches nobody whose vault sits elsewhere. `vault/` mirrors the vault root, so **adding a skill or a doc is adding a file**. **`AGENTS.md` IS THE FRAMEWORK'S AND `INSTRUCTIONS.md` IS THE PERSON'S.** The guide used to be one file with two owners — the framework's paragraphs seeded once, and then somebody's own text around them — so the framework's half went stale exactly as a skill did and the person's half could never be rewritten. Now `AGENTS.md` is the format, rewritten on every open with the skills and the docs, and its first line sends the agent to `INSTRUCTIONS.md`, which the seeder fills once as a stub and nothing ever touches again. A vault that had an `AGENTS.md` of its own gets the framework's written over it like any unit — the vault is committed before the first write, so what stood there is one `git show` away, and the person moves what was theirs into `INSTRUCTIONS.md` by hand; the framework does not read a guide to decide whose it is, which is the same breaking change, not carved around. `docs/` takes the same rule outright: it is the manual, written for the person and not by them. It is a plain `.agents/skills/`, not `.claude/skills/`: the folder has to read the same to Claude Code, Cursor and Codex, and the vault's `AGENTS.md` is what points at both. **THE TWO ARE NOT THE SAME FOLDER AND THE LINE BETWEEN THEM IS A RULE**: `docs/` says how the thing WORKS and is written for the person whose workspace it is; a skill says how we WRITE with it and what the checker will say, and carries every numbered rule, because the number is the join between the prose and `check.ts`. A passage is in exactly one of them and each links the other — `vault/.agents/skills/biom-docs/` is that line, stated for the vault. **Changing any of it is its own subject** — `INSTRUCTIONS.md`, `design/` and `base/` are seeded additively and never updated, while `AGENTS.md`, `docs/`, the skills, the checker and its `_lib/` are the FRAMEWORK'S inside a vault and are REWRITTEN WHOLE on every open by `rewriteOwned` in `server/workspace/framework.ts`, off the mount path, committed before the first write and once after naming the framework version: a skill cannot be overridden, a change to one made in a workspace is gone on the next open, and a workspace adds skills under names of its own, which the rewrite never touches. **WHICH IS WHY EVERY FRAMEWORK SKILL DIRECTORY WEARS `biom-`** — `SKILL_PREFIX` in `server/workspace/framework.ts`, held equal to `tests/skill.test.ts`, which refuses a shipped skill without it: `pages` is a name anybody would give a skill of their own, and a workspace's `pages` must never be rewritten as the framework's, so the framework's is `biom-pages` and the frontmatter `name:` an agent routes on is the directory. A copy under the OLD bare name is left where it stands — it is a name the framework no longer uses, so it is the workspace's now, and the workspace deletes it; a vault seeded before the prefix carries every skill twice until somebody does, which is the breaking change said above, paid once. A skill and the checker are one statement in two places, and the only real test of a skill is building a page from it. `.agents/skills/vault-skills-guide/` owns that.

**`skill/check.ts` runs in two places, so its imports go through `skill/_lib/`.** Here that directory re-exports the real modules; in a vault `rewriteOwned` writes verbatim copies beside the checker on every open, because a vault has no `contracts/`. Copying the checker alone shipped a command that could not run — `bun run .agents/skills/check.ts` is the one command the vault's `AGENTS.md` tells every agent to run, and it died on module resolution while a test asserting the file existed stayed green. **Assert that it runs, never that it is there.**

**No literal NUL bytes in source.** `make check` fails on them and names the file. A NUL is legal JavaScript and completely invisible, and it makes grep treat the whole file as binary — so every search of it returns nothing rather than something wrong. It has cost two wrong diagnoses here, one of them a regression reported in a file that had lost nothing. Write `\u0000`.

**Fixtures are invented and say so.** Any trade figure, job name or worked example anywhere in this repo represents nothing real.

**THE SUITE IS TWO SUITES AND THEY CATCH DIFFERENT CLASSES OF FAULT.** `make test` is `bun test` over `tests/*.test.*` — every module against its own invariants, eleven seconds, and it is the gate before every commit. `make e2e` is `tests/e2e/`, and it is *the program, assembled, on a screen*: the files end in `.e2e.ts` so `bun test`'s own discovery — `.test.`, `_test_`, `.spec.`, `_spec_` and nothing else — walks straight past them and `test` stays fast, and the Makefile names them explicitly with a `./` in front, because bun reads a bare path as a filter against that same glob and finds nothing. **A fault that is only visible in the assembled program has to be caught there**: a remembered vault opening instead of the picker, a stack trace on every launch, Electron's own menu bar, a rail row that was in the source and not in the build. Every one of those was green in the whole unit suite. **`make e2e` is not a prerequisite of `test` and does not become one** — it needs a browser and takes minutes — and it is run for real before a release.

**Layer one is the server; layer two is the bundle; neither is the other with something added.** `tests/e2e/server.e2e.ts` runs `server/main.ts` the way `make dev` does and drives it in a headless Chromium — the picker on a first launch, creating a workspace through the wire, the seeded copy and the Dashboard row, the root page's modules and its two Copy controls really writing to the clipboard, its Design link routing to the design doc, a page made through New, the live redraw from a file written outside the app, the rail learning about a directory nobody told it about, a half-written save and the finished one, the markdown mirror, and opening a workspace already on disk. **The clipboard is that layer's alone**: the permission is delegated to a frame with an opaque origin, which is a fact about the assembled program and invisible to every unit test. **`tests/e2e/startup.e2e.ts` is layer one's other half**: the same server, in the same browser, started against a workspace that has gone wrong — deleted, on a volume that is not mounted, a file now, unreadable, a `workspace.db` that is not a database, a vault format this build does not read, and a remembered list that will not parse. It cannot share layer one's server, because every state in it is about what the process does ON THE WAY UP, so each is its own launch; what every one of them asserts is the same four things — the server answers at all, the PICKER is on the screen, one plain sentence is on it, and what was on disk is still on disk. `tests/e2e/app.e2e.ts` starts `dist/out/Biom-…/Biom` and asks the window it opened — the ready line, our title bar and its four controls, `window.biomShell`, the token refusal, the production hide list, maximise and full screen, and close taking the server with it and leaving no process of it running — which it asks `pgrep` rather than the socket, because a server mid-exit answers nothing and is still a process holding a workspace open. **Its last step is a second launch** whose remembered workspace has become a file: the symptom there was not a bad screen but NO WINDOW, so it is a fact about the bundle and about nothing the first layer can see. **It skips itself with a named reason where there is no bundle or no screen**, and never fails for either; `make app` makes the first, and on Linux it takes a display of its own through `xvfb-run` where there is one. The CI job builds the bundle, so a skip cannot be what makes the runner green.

**A SCREEN IS NOT A DESKTOP, and the step that needs the difference says so.** `Xvfb` is a frame buffer with nobody on it: maximise and full screen are not things a window does to itself — the application sets `_NET_WM_STATE_MAXIMIZED_*` or `_NET_WM_STATE_FULLSCREEN` and a **window manager** honours it — so on a bare virtual display the request is made, nobody answers, and the state never changes. That is a fact about the display and not about the application, which is why it passed on a developer's desktop and failed the first time CI ran it. **`tools/screen.sh` sits between `xvfb-run` and the application**: it starts openbox (or fluxbox, or icewm — the first one installed), waits for it to actually take the root window, and execs the bundle. `--probe` is the same code path with nothing to exec, and `app.e2e.ts` asks it that at load: **where no manager can be had, the maximise and full screen step alone is skipped by name and everything else is walked.** The CI job installs `openbox` and `x11-utils` beside `xvfb` so the step is real there. A machine whose display already has a manager — anybody's desktop — is left alone rather than given a second one.

**Every launch either suite makes gets a data directory of its own, and it is checked rather than trusted.** `HOME`, `XDG_DATA_HOME`, `XDG_CONFIG_HOME` and `LOCALAPPDATA` are all pointed at a temporary tree — three programs answer *where does my data live* three different ways, and Electron writes its own profile under the config one — and `outside()` in `tests/e2e/harness.ts` reads the REAL directory before and after to prove nothing reached it. That is not hygiene: agents' test runs had written a scratch vault into the person's own remembered list, and the packaged application then opened it instead of the picker. **Never start a server or an application from a test without going through `sandbox()`.**

**Layer two speaks CDP itself rather than through Playwright, and that was measured rather than preferred.** `chromium.connectOverCDP` asks Electron's BROWSER-level endpoint for a shape it does not answer: the socket opens, the handshake never completes, and it arrives as a timeout with nothing in it to read. The PAGE-level endpoint is an ordinary DevTools target and answers everything the walk needs, so `cdp()` in the harness is a small client over a raw socket. **Every wait in both files is bounded and says what never happened**, and a failing step names itself, its screenshot under `dist/e2e/` and what the process said on stderr — those three are the whole of what somebody needs to act on an end-to-end failure, and none of them is in the assertion.

**Third-party code is served, never bundled, and reached by a bare specifier.** `client/index.html` carries an import map so `import MarkdownIt from "markdown-it"` stays bare — which the gate already skips as a package, so vendoring added no edge to the dependency graph. `bun` and `tsc` resolve the same name through `paths`, pointed at `./vendor/markdown-it` **without an extension**, because naming the `.mjs` exactly makes TypeScript check 800 lines of minified bundle instead of the declaration beside it.

**A vendored file is verified in a browser, not in a test runner.** The Node build of markdown-it was vendored here once by mistake; it passed `tsc` and every unit test and could not be loaded by any browser, because those two resolve through `paths` and the browser resolves through the import map. Different mechanisms, and only one of them is the product.

**An artifact may load a classic script from `/vendor/`, and only from there.** A sandboxed frame has an opaque origin: a classic `<script src>` loads, while `fetch` and a **module** script are both blocked — measured, not assumed. So the frame can RUN host-served code without being able to READ anything back, and the chokepoint, which is about data, still holds. R35 in `vault/.agents/skills/biom-sections/SKILL.md` carries the rule and `vault/docs/code.md` carries the measurement behind it; `three` is 706KB, so a library is fetched on the branch that genuinely needs it and never otherwise. **Nothing in `guest/plugins/` reaches `/vendor/` any more** — the shipped set draws with the platform and nothing else, and a heavy library is a workspace's own choice made in its own plugin file.

**THE AGENT TERMINAL IS A SHELL THE SERVER OWNS, BESIDE THE PAGE AND NEVER INSIDE IT.** A person runs their own agent CLI in the vault's folder in a real PTY (`Bun.spawn` with `terminal`), drawn by xterm.js in the HOST — no page contract gains a kind, `contracts/` is untouched, and the wire is spelled twice (`server/workspace/terminals.ts`, `client/transport/terminal.js`) with a test holding the two equal. **Visibility is not lifetime**: hiding, docking to another edge, full screen, switching page or tab and reloading send nothing, so none of them can stop a process; `end`, the shell exiting, the server going and the orphan rule (no client for two minutes) are the only endings, and every tree is killed in the server's `exit` handler. **The route is guarded in every build, source runs included**, because it is command execution and `Bun.serve` listens on every interface: WebSocket upgrade, launch token, loopback peer, loopback Host with a matching Origin, and a per-launch `HttpOnly; SameSite=Strict` capability cookie set only on the composed document — `terminalRefusal` in `server/main.ts` — and the page proxy strips `set-cookie`. **The dock never moves the page**: `.work` holds the bed and the dock as two fixed children and the edge is a grid template on it, exactly because moving an iframe reloads it. The Agent Terminal row is in every build — it is not a diagnostic. `.agents/skills/terminal-guide/` is the mechanism, the limits and what is deliberately not built.

**The rail's foot holds the workspace's own screens, and one of them is a plugin page with no directory at all.** Design, then Instructions and Automations (the paragraph above), then the Map, then Close workspace. The Map row draws the whole workspace with the `mindmap` plugin — the vault's own copy of it, like every other plugin — mounted on `MAP_PAGE` (`@map`, beside `DESIGN_PAGE` in `contracts/wire.js`): `page.read` answers it as a bare plugin page — no sections, no variables, `input.rail` set, the document read live out of `<vault>/plugins/mindmap/` — so the runtime draws nothing over the plugin and nothing is ever written for it. A page that wants a map of its own says `plugin: mindmap` and is an ordinary page whose settings live in its variables. Adding the route widened `ViewName` in `contracts/types.ts` by one member; that was the one contracts edit, and it is recorded here because the file is otherwise frozen.

**A box may draw another page inside itself, and the sandbox is kept.** `page.embed` on the guest port is answered with the target page's woven document and two transferred ports minted for it; the box relays the handshake into a nested `srcdoc` iframe — `biom.embedInto` — and the nested page draws with its own runtime, as opaque as the box it sits in. `boundary-guide` §9 is the mechanism. That was the second contracts edit: `page.embed` joined `HostRequest` and `unembed` joined `GuestNotice`, together, at one barrier.

**A GRID IS THE DOCUMENT'S OWN TABLE, AND IT WAS THE SIXTH CONTRACTS EDIT**, taken at its own barrier on 2026-09-17 for the workspace's *Table sections* spec: `grid` joined `ContentType`, `PartKind` and `Part`; `Content` gained `rows` and `head`, the one value in the format that is not a string; and `section.write` widened to carry `string[][]`, with `isRows` in `guards.js` beside it. Nothing else on the wire moved. A markdown table is a run of pipes inside a paragraph — drawn as a thin strip of wrapped sentences, edited by retyping the pipes — and the earlier route, a plugin redrawing every markdown table in place, was built in the workspace and taken out again because it changed how a table looked and nothing about how it was edited. So a table is a PART KIND: its rows are a list of lists of markdown strings in `content.yaml`, written back one row per line, `- [Piece, Where]`; `plugins/biom-grid.js` draws them as a board and edits them a cell at a time, with *Delete row*, *Delete column*, *Add row* and *Add column* in a gutter outside the board that says which; a write from the board goes down `section.write` whole and **redraws nothing**, because the board drew what it changed before it asked; the projection writes it into the mirror as a markdown table again, pipes escaped; and `guest/sections/default.html` widens to the figure width when its one slot holds one, off a `data-g-kind` the runtime now puts on every filled slot. **The doc plugin converts, once, in place**: `guest/plugins/biom-doc/index.html`'s second script finds a markdown table in a prose part on every draw and rewrites the document through the runtime's own port — the prose before keeps the section's name, the grid is `<name>-table`, the prose after is `<name>-after` — so nobody retypes anything and a document with no table is never touched. It is not the `table` part, which names rows the server holds in `workspace.db`; `vault/docs/tables.md` says which to reach for, R62 to R64 in `skill/check.ts` say what is wrong with one, and `tests/grid.test.ts` walks the kind from the guard to the mirror. **What was deliberately NOT taken with it** is the rule that a write from the page does not redraw the page — one version on the document and the drawn page — which the workspace holds as its own spec.

**Deleting the Config screen and the two panels was the FIFTH contracts edit**, taken at its own barrier on 2026-09-17, and it was a removal: `pageView` and `panel` left `UiState`, and `readDocRaw` and `writeDocRaw` left `WorkspaceStore`. A field nothing reads is a door any caller can open, and a method nothing calls is a promise the store need not keep. The `doc.raw` and `doc.writeRaw` wire kinds stayed, because the API is not a screen — `tests/integration.test.ts` writes whole pages through them the way an agent's tool would.

**AUTOMATIONS AND RUNS WERE THE EIGHTH CONTRACTS EDIT**, taken at their own barrier on 2026-09-17 for the workspace's *Automations* spec, and `.agents/skills/runs-guide/` is the guide. **An automation is a folder under a page — `automations/<name>/` holding a thin `automation.yaml`, a `kickoff.md`, its own `INSTRUCTIONS.md`, `skills/` and `code/` — and a run is a process the server starts from it, in a directory of its own under `.biom/runs/<id>/`, with a row in `.biom/runs.db` and two logs that outlive it.** The framework holds the mechanism and nothing about what a run means: it knows no agent by name, parses no log, resumes nothing, and the manifest is the only file in the folder it reads. Six kinds joined `HostRequest` — `automation.list`, `run.start`, `run.list`, `run.get`, `run.read`, `run.kill` — because a page may see every automation, start any, follow any run's log and end any: THE RING IS NOT THE WALL, and what will narrow a list, a row and a log is the asker's view permission on the row's `page`, from the sync engine's model, for which this build carries no filter and no seam. `run.live` and the page-file, manifest, template, environment-name and vault-file kinds joined the outer ring; `uid` joined `PageRef` and `PageDoc` — minted on create, written into every page that has none on mount, kept through a move, and named by every run so a moved page still owns its runs; `runs` and `instructions` joined `ViewName`, and `pageView` came back to `UiState` — the fifth edit had taken it out with the Config screen — three members wide, `page`, `instructions` and `automation`, every one of them in every build. **`INSTRUCTIONS.md` is the person's file at three levels and `AGENTS.md` is the framework's at every level**: the vault's is seeded, the run's is generated and is what a harness finds first, naming the three in the order they outrank each other — so the kickoff is the author's file, substituted and nothing more. **`.biom/` is the framework's folder inside a vault and it ignores itself**; `runs.ts` is the third file allowed SQL and `db.ts`'s header says so; the watcher excludes `.biom` by name so a log growing never redraws a page; a run starting or ending is one payload-free event on the vault's stream; a run's rows are re-pointed by the registry when its page moves (`relocate` beside `restack`, `relocateAll` by identity on mount and on a structural burst) so no read walks the page list; and a row is alive by its pid AND the process's birth, so a pid reused after a reboot is `lost` rather than counted, held for and killed. **No run outlives the server**: every automation is a process group of its own, so the registry ends them gracefully on `SIGINT`, `SIGTERM` and when the shell's stdin pipe closes, kills whatever is left synchronously in the process's `exit` handler beside the terminals' — the one ending every route passes through — and a row it could not update reads `lost` on the next mount. **Closing the window over a live run asks**, in the bar, and yes is the one way past the hold. The rail's foot gained Instructions and Automations, the page bar gained the same two words as controls — BEFORE the terminal's toggle, which stays the rightmost action — all four in every build; every editor on those screens autosaves QUIETLY under one commit taken as the file opens, and a name is asked in a field in place, never by `window.prompt`, which Electron's renderer throws on; and the seeded root page's recurring asks now say to make the thing an automation and that there is no clock here. Dependencies, containers, a scheduler and access are deferred by decision and the guide says where each will land.

**THE WHOLE TREE IN ONE REQUEST WAS THE NINTH CONTRACTS EDIT**, taken at its own barrier on 2026-09-20, and it is one kind on the outer ring: `children.all` joined `ApiRequest`, answering every page's children keyed by id, root included, and `childrenAll()` joined `Pages` to walk the tree once for it. **The store's `readChildren` used to ask `children` once per page** — "a throwaway instrument's kind of cost" on a few dozen pages, which the comment said out loud — and on a workspace of eighteen hundred pages that was more requests than a browser will have in flight: refused before the server heard them, so the shell said the server had not answered while the server sat idle. Now it asks once. Each entry is exactly what `children(id)` answers for that page, read by the same `childrenOf`, so a box drawing its own children and the rail drawing the tree can never disagree; a page whose children could not be read answers an empty list rather than taking the whole map down. `children` itself is untouched and stays on `HostRequest`: a box asks about the page it is on and nothing wider, and the tree is the shell's — which is why the new kind is on the outer ring and no guard learned it. `tests/api.test.ts` holds the map to the per-page answers, and `tests/store.test.js` holds the count to one request per tree read.

**A redraw keeping the reader's place was the FOURTH contracts edit**, taken at its own barrier on 2026-09-15: `position` joined `GuestNotice` and `place` joined `HostEvent`, together, with `keep` on `FrameHost` beside them, and `isGuestNotice` learned the one notice. Nothing else could carry it — the box is the only side that can measure its scroll and the host is the only side that outlives the realm a redraw tears down — and a page in the wild is untouched, because both messages are the shim's and the host's and no section says either. The paragraph on the watcher above is the mechanism.

**SHARE A PAGE was the SEVENTH contracts edit**, taken at its own barrier on 2026-09-17 — the fifth was the deletion and the sixth the grid, and three branches each called theirs the fifth until they met on main: `page.share` joined `ApiRequest` carrying a page id and, optionally, the page's drawn document, and `Share` is its answer; neither guard learned anything, because the box never asks for it — the workspace UI does — so no page in the wild can say it. **It is a stop-gap and is written to be thrown away**: the hosted server makes every page viewable at a URL, and until then a teammate needs a link. **The tab cannot capture the page it shows** — the box has an opaque origin and the host cannot see in, which is the boundary working — so the capture is taken by whichever side CAN see in, and there are two. **In the built application it is the shell**: the main process reaches the box through `webContents.mainFrame.frames`, and `biom:capture-page` in `app/main.js` serialises the page the person is looking at — scripts out, every canvas turned into its picture, every section marked in view so a scene below the fold plays for a stranger, and the sheet's paper written in because the box is transparent — then `app/preload.js` hands it to the page as `capturePage()`, the fourth key on the bridge, and the client sends it up in the request. **In a browser tab it is the server**: `server/platform/capture.ts` opens the server's own address in the Chromium that `make browser` installs, waits for the strip to read `Drawn`, scrolls the page through once, and reads the frame through Playwright — which is a development dependency, so a compiled build is handed no capture of its own and refuses in words when nothing was handed over. Either way `server/domain/share.ts` makes the text stand alone — every font `faceCss` wrote absolute and every relative `src` under the `<base>` become data urls out of files the server already holds, the base tag goes, and what could not be folded in is NAMED in the answer rather than left to break silently — and `server/platform/bucket.ts` puts it in `biom-shares` under a uuid through Bun's own S3 client, so nothing was added to the dependencies. **The id is the whole of the security**, and the spec says so. The five names the bucket needs come out of the environment, and every build also reads `~/.config/biom/share.env` when the environment has none of them, because that is the file the provisioning script writes, a desktop launcher hands the process no environment of the person's, and it is never in a repository. The Share tool sits beside Reload in every build, says `Sharing…` while the capture runs, and hangs the link off itself with Copy and Open. `Specs/2026-09-16-Share_A_Page` in the internal workspace is the decision record.

**`vault.info` moving into `HostRequest` was the THIRD contracts edit**, taken at its own barrier on 2026-09-14 — the argument for which ring it belongs in is in the rings section above, and the kind's own doc comment in `contracts/types.ts` carries it too. Nothing was added: the kind already existed on `ApiRequest` for the picker, and what changed is which ring a page can reach it from, so the edit is one member moved between two arms of the same union plus its line in `guards.js`. `biom.vault()` is the wrapper, the bridge answers it out of the store the workspace's own screens read, and the seeded root page is its first caller — the root used to send a stranger to Modify page for the folder and now prints it in the band.

**`design/` is a page-shaped root beside `pages/`, and that placement is the design.** The rail draws `pages/`, so the design doc is out of the tree by construction — no reserved sidecar key, no hidden-id list, no third page kind. **It is an ORDINARY PAGE reached by a reserved id**: `DESIGN_PAGE` is `@design`, `pageDir` sends that id to `design/` and nothing else in `pages.ts` learned that this file exists, so reading it, writing a slot, reordering, removing a section and patching a scope all came for free. `@` is outside a page segment's grammar, so it can never collide with a page somebody makes — which is also why the id is not the bare word `design`, a perfectly legal one for a page of their own. `makeDesignView` is a MOUNT and nothing else: the same document, the same runtime, the same wave, keyed apart so the design box and a page called `design` are two boxes. The `design.*` wire kinds predate that and still answer on `ApiRequest`; they are no longer how the client draws it.

**One half of it is not whole, and it is the page's own DOCUMENT.** `makeDesignView` weaves an empty document rather than the page's, because the host's snapshot has no design page in it to read an `html` off — so `design/index.html` is resolved by the server and never loaded, and the design doc is always drawn by the `doc` plugin. Everything a design page shows is therefore a SECTION, which is what the seeded one is: a masthead, the shipped palette drawn small, and three full-bleed worlds, each carrying its palette in its own `variables` and its markup in a file beside `content.yaml`. What it would take for the design page to draw its own document is the shell reading `@design` through the store like any other page and handing the result to the page view — a client change, at no barrier, wanted only when a design doc has a shape a stack of sections cannot make.
